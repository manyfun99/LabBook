### 1.2 문제점

- 문제 1 — **사용자 확인이 `select` 의 사람 검토를 겸하는데(2차 §2.2), 확인할 재료가 없다.** `select` 는 레포 이름만 출력한다. 점수, 동점 여부, 경계에서 밀린 레포를 보지 않으면 순위가 타당한지 판단할 수 없다.
- 문제 2 — **후보를 뺄 수단이 없다.** 사용자가 후보 하나를 빼고 싶어도 `select` 에는 제외 옵션이 없다.
- 문제 3 — **심층분석 15~19개를 한 대화 컨텍스트에서 돌리기 어렵다.** 레포마다 clone, 코드 구조, 이슈 수십 개, 포크, 웹 검색을 읽는다. openbb·ai-hedge-fund 처럼 큰 레포도 있다. 한 세션에서 차례로 돌리면 컨텍스트가 앞 레포 원문으로 차고, 뒤 레포일수록 품질이 떨어진다.
- 문제 4 — **스킬의 `signal` 적재 명령이 깨진다.** 인용을 SQL 문자열 리터럴로 넣는다. 영어 이슈 원문의 작은따옴표(`don't`, `it's`)에서 SQL 이 깨지거나, 사람 손으로 이스케이프하다가 원문이 바뀐다.
- 문제 5 — **인용이 원문인지 검사하는 장치가 없다.** 스킬은 "원문 그대로 인용"을 요구한다(1·2단 판정에는 인용 검사가 코드에 있다). 신호는 브레인스토밍의 유일한 수요 근거라서, 요약문이 인용으로 섞이면 원페이저의 근거가 흔들린다.
- 문제 6 — **T 면책 편향.** 판정기는 README 면책 문구("연구용", "투자 조언 아님")를 "성과를 주장하지 않는 도구"로 읽어 T 를 높게 줬다(인계 §2 사실). 전수 판정 T 는 66% 가 5점이다. 스킬의 "성과 주장의 신뢰도" 절에는 이 편향을 바로잡는 지침이 없다. 그래서 노트도 같은 편향을 따를 수 있다.
- 문제 7 — **`weight` 정의가 모호하다.** "반응·댓글 수"라고만 적혀 있다. 레포마다 세는 방식이 다르면 브레인스토밍에서 반응 합계를 비교할 수 없다.

## 2. 목표

### 2.1 달성 목표

- 사용자가 점수와 경계 정보를 보고 후보를 확정한다(`select --confirm`, `--add`).
- 확정한 레포 전부에 대해 심층분석 노트와 `signal` 행을 남기고, `export`·커밋한다.
- 노트에서 T 를 면책 편향 없이 다시 보고, 판정 T 와 대조한 표를 남긴다. 이 표는 이후 "판정 견고성" 계획(인계 §3.0-3)의 T 루브릭 개정 근거가 된다.

### 2.2 성공 기준

- 사용자 확인 결과(그대로 확정, 또는 뺀·더한 레포와 사유)가 `log.md`·인계 문서에 기록된다. 사람 검토의 기록은 이것으로 대신한다.
- `screening(deep, include)` 행 수 = 15 + 새로 더해진 `--add` 수 − 뺀 수. 이미 후보에 있는 레포를 `--add` 하면 `select` 가 건너뛰므로(`report.py:45`) 셈에 넣지 않는다.
- `deep` include 레포마다 노트 `notes/<owner>__<repo>.md` 가 있다. 노트에는 frontmatter(`entity`·`gh_id`·`judged`·`rubric`·`t_deep`·`tags`)와 6개 절이 모두 있다. 수요 신호가 0개인 레포는 수요 신호 절에 "없음"과 그 사유를 적는다.
- `signal` 행은 모두 인용 대조(§3.4)를 통과한다. 이슈·댓글·README 출처는 스크립트로 전수 대조한다. 그 밖의 출처는 사람이 하나씩 확인한다. 불일치는 0건이어야 한다.
- `index.md` 에 노트마다 한 줄이 있고, `log.md` 에 레포마다 `deep-dive` 줄이 있다.
- 퍼널 리포트 `reports/funnel-*.md` 의 `심층분석 N` 이 `deep` 행 수와 같다.
- 판정 T 와 심층 T 를 대조한 표를 인계 문서와 PR 본문에 싣는다. 차이가 2 이상인 레포 수도 적는다. 판정이 없는 레포(worldmonitor 등)는 판정 T 를 "-"로 두고 차이 집계에서 뺀다.
- `data/*.jsonl` 을 커밋하고, 빈 DB 에 `import` 했을 때 행 수가 같다.
- 전체 테스트 135개가 통과한다(코드 무변경 회귀).
- 일정: 브레인스토밍 판정일(원 계획 §2.3, 2026-10-24)보다 충분히 앞서 끝나야 한다. 목표는 2026-10-05 이전이다.

## 3. 해결 방안

### 3.1 `select` 확인 — 후보표 한 장 + 버튼 두 문항

드라이런 결과에 점수와 경계 정보를 붙여 한 장의 표로 보여 준다. §1.1 의 후보표와 "경계에서 밀린 레포" 목록이 그 형식이다(메모리 `prefer-minimal-actionable`). 표 위에 세 줄만 붙인다: ① P 슬롯은 T 가 모두 5 라서 ★ 순으로 정해졌다 ② 라이징 슬롯에는 점수 하한이 없다(mirofish P2 T1) ③ 의심 표시는 `low_watchers` 뿐이다.

표는 SQL 로 만든다. 슬롯별 상위와 경계 레포는 `report.py` 의 `ORDER` 식을 그대로 쓴다.

```sql
SELECT replace(key, 'github:', '') AS repo, category, market, P, I, N, T, stars, d30, flags, injection_suspect
FROM v_repo_latest WHERE topic = 'stock-oss' ORDER BY P DESC, T DESC, stars DESC LIMIT 12;  -- I·d30·kr 도 같은 식
```

AskUserQuestion 두 문항을 한 번에 묻는다.

| 문항 | 형식 | 선택지 |
|---|---|---|
| 후보 15개 | 단일 선택 | ① 그대로 확정 (권장) ② 빼거나 바꿀 레포 있음 — "Other"에 레포 이름과 대체 레포를 적는다 |
| `--add` | 복수 선택 | koala73/worldmonitor(사용자 스타, 1단 제외) · dragon1086/prism-insight(사용자 스타, kr, P4 N5) · hkuds/vibe-trading(사용자 스타, 라이징 5위) · chrisryugj/korean-dart-mcp(kr, P5 N5, 동점으로 밀림). 질문 문구에 "추가하지 않으려면 Other 에 '없음'"을 적는다(선택지는 4개가 상한이다). 그 밖의 레포도 "Other" 로 받는다 |

확정은 다음 순서로 한다.

```sh
python3 -m labbook select stock-oss --add <고른 레포…>            # 먼저 드라이런
python3 -m labbook select stock-oss --add <고른 레포…> --confirm
```

- 드라이런에서 `수집되지 않은 레포: …` 로 끝나면(`report.py:43-44`), 그 레포는 이번 범위에서 뺀다고 사용자에게 한 줄로 알린다. 그리고 나머지로 확정한다. 수집을 다시 돌려 넣는 것은 이번 조각에서 하지 않는다.
- 드라이런 출력에 `user` 로 나오지 않은 `--add` 레포는 이미 다른 슬롯에 있는 것이다. 이것도 한 줄로 알린다.

- 뺄 레포가 있으면 코드를 고치지 않고 확정 직후 SQL 로 처리한다(2026-09-28 사용자 확정). 확정된 `deep` 행을 `exclude` 로 바꾸고, 원래 슬롯을 사유에 남긴다. 심층분석 대상 SQL 은 `decision='include'` 만 고르므로 이 레포는 대상에서 빠진다. 대체 레포는 `--add` 로 넣는다(`slot=user`). 빈 슬롯을 다음 순위로 자동으로 채우지는 않는다. 사용자가 대체 레포를 직접 고르는 편이 의도에 맞는다.

```sql
UPDATE screening SET decision = 'exclude', reason = 'user-drop:' || reason
WHERE topic = 'stock-oss' AND stage = 'deep' AND decision = 'include'  -- 두 번 돌려도 사유가 겹치지 않게
  AND entity_id = (SELECT id FROM entity WHERE key = 'github:<owner>/<repo>');
```

- 사용자 결정은 `log.md` 에 `## [날짜] select-review | 그대로 확정` 또는 `| drop owner/repo(사유) · add …` 로 한 줄 남긴다. `select --confirm` 이 자동으로 남기는 줄과는 별도다.
- `funnel` 은 확정 **뒤에** 한 번 돌린다. 앞에 돌리면 `심층분석 0` 인 리포트가 남기 때문이다. 퍼널에는 `오류 1(재시도 대기)`(idouble)이 보이는데, 판정 견고성 계획에서 다루므로 이번에는 `judge` 를 다시 돌리지 않는다.

### 3.2 심층분석 분할 — 레포당 서브에이전트, 5개씩 배치

레포 하나를 서브에이전트(Agent, general-purpose) 하나가 맡는다(2026-09-28 사용자 확정). 서브에이전트는 노트와 신호 후보 파일만 쓴다. DB·`index.md`·`log.md` 는 메인 세션이 배치 단위로 한 번에 갱신한다.

| 배치 | 대상 | 비고 |
|---|---|---|
| 1 (파일럿) | P 슬롯 5 | 데이터 라이브러리라 구조가 단순하다. 형식·소요를 여기서 잰다 |
| 2 | I 슬롯 5 | |
| 3 | 라이징 3 + 한국 2 | |
| 4 | `slot=user` 전부(추가분·대체 레포). 5개를 넘으면 5개씩 나눈다 | worldmonitor 는 `judgment` 가 없다. 서브에이전트에 1단 판정(`exclude`·`unrelated`)을 맥락으로 준다 |

배치마다 메인 세션이 하는 일:
1. 대상 SQL(스킬 "대상")에서 `index.md` 에 카탈로그 줄이 없는 레포를 고른다. 완료 기준은 노트가 아니라 이 줄이다. 메인은 신호를 적재한 뒤 마지막에 이 줄을 쓴다(4번). 그래서 노트만 있고 줄이 없는 레포는 서브에이전트를 다시 띄우지 않고 3번(검수)부터 이어서 한다. 노트가 쓰인 뒤 적재 전에 세션이 끊겨도 신호가 빠지지 않는다. 적재는 `INSERT OR IGNORE` 라 다시 해도 안전하다. 노트·신호 파일 이름의 `<owner>__<repo>` 는 `entity.key` 에서 `github:` 를 뗀 **소문자** 값으로 한다. GitHub 표시명(`OpenBB-finance`)을 쓰면 노트 유무 확인이 어긋난다.
2. 서브에이전트 5개를 한 메시지에서 병렬로 띄운다. 프롬프트에는 다음을 넣는다: 스킬 전문, 레포 키·`entity_id`·`gh_id`, 판정 행(`v_repo_latest` 의 점수·요약·`judged_at`, 그리고 뷰에 없는 축별 인용은 `judgment.evidence`), 노트와 신호 파일 경로, "DB·`index.md`·`log.md` 에 쓰지 말 것", 최종 보고 형식(10줄 이내: 판정 T/심층 T, kind 별 신호 수, 조사 불가 항목, 의심 사항).
3. 검수: 노트 형식(frontmatter 필드·6개 절)을 확인하고, 인용 대조(§3.4)를 돌린다. 불일치 신호는 버리거나 원문으로 고친다. 형식이 어긋난 노트는 그 서브에이전트에 SendMessage 로 고치게 한다.
4. 신호 적재(§3.3 스크립트) → `log.md` → 마지막에 `index.md` 줄, `export`, 커밋 `docs(stock-oss): 심층분석 배치 N — owner/repo …`.

파일럿 게이트: 배치 1 뒤에 한 번 멈춘다. 배치 소요, 노트 하나의 경로, 신호 수를 한 줄로 보여 주고 버튼으로 묻는다: "계속 진행 (권장)" 또는 "노트 형식 조정". 조정을 고르면 그 내용을 스킬에 반영하고, 배치 1 노트도 새 형식에 맞게 고친 뒤 진행한다. 그 뒤로는 멈추지 않는다.

조사 예산 (레포당, 스킬에 적는다): 이슈는 반응순 상위 30개와 댓글순 상위 30개를 본다(`gh search issues --repo <r> --sort reactions`·`--sort comments`, 열린 것·닫힌 것 모두). Discussions 가 켜져 있으면 GraphQL `discussions(first: 50, orderBy: {field: UPDATED_AT, direction: DESC})` 로 받는다. 그중 `upvoteCount` + 댓글 수 상위 10개를 본다(GraphQL 에는 반응순 정렬이 없다). 포크는 ★순 상위 10개(`gh api repos/<r>/forks?sort=stargazers`)를 본다. 상용 파생을 찾는 웹 검색은 3회 이내로 한다. 이 예산은 컨텍스트와 search API 한도(30/분) 안에서 5개를 병렬로 돌리기 위한 것이다.

외부 호출이 실패할 때의 거동 (스킬에 적는다):
- `git clone`·`gh api` 오류: 1회 다시 시도한다. 그래도 실패하면 해당 절에 "조사 불가(오류 요지)"를 적고 보고에 올린다. 노트는 나머지 절로 완성한다.
- search API 레이트리밋(403·`rate limit`): 60초 기다린 뒤 다시 시도한다. 두 번째도 걸리면 위와 같이 "조사 불가"로 둔다.
- 메인은 "조사 불가"가 있는 레포를 배치 끝에 한 번 더 서브에이전트로 보강한다. 그래도 안 되면 인계 문서에 적는다.

### 3.3 스킬 갱신 — 신호 파일 + 파라미터 바인딩 적재, `weight` 정의

`labbook-deep-dive/SKILL.md` 의 출력 2번(신호 행)을 바꾼다. 대화형으로 한 개를 돌릴 때도 같은 방식을 쓴다.

현재:

```sh
sqlite3 labbook.db "INSERT OR IGNORE INTO signal (topic, entity_id, kind, quote, source_url, weight, found_at)
VALUES ('<주제>', <entity_id>, 'demand', '<원문 인용>', '<URL>', <반응 수>, datetime('now'));"
```

개선: 신호는 `.cache/signals/<owner>__<repo>.jsonl` 에 한 줄씩 쓴다(`{"kind", "quote", "source_url", "weight"}`). 적재는 파라미터 바인딩으로 한다. `found_at` 은 다른 테이블(`decided_at` 등)과 같은 ISO 형식이 되도록 `labbook.db.utc_now()` 를 쓴다. 기존 `datetime('now')` 는 `2026-09-28 01:37:47` 형식이라 다른 테이블의 `2026-09-27T01:37:47+00:00` 과 어긋난다.

```sh
python3 - labbook.db <주제> <entity_id> .cache/signals/<owner>__<repo>.jsonl <<'EOF'
import json, sqlite3, sys
from labbook.db import utc_now
db, topic, entity_id, path = sys.argv[1], sys.argv[2], int(sys.argv[3]), sys.argv[4]
conn = sqlite3.connect(db)
with conn, open(path) as f:
    for line in filter(str.strip, f):
        s = json.loads(line)
        assert s["kind"] in ("demand", "pain", "gap"), s
        conn.execute("INSERT OR IGNORE INTO signal (topic, entity_id, kind, quote, source_url, weight, found_at) "
                     "VALUES (?, ?, ?, ?, ?, ?, ?)",
                     (topic, entity_id, s["kind"], s["quote"], s["source_url"], s["weight"], utc_now()))
print(conn.execute("SELECT COUNT(*) FROM signal WHERE entity_id = ?", (entity_id,)).fetchone()[0])
EOF
```

- 레포 루트에서 실행한다(`labbook` 패키지 import). 첫 인자가 DB 경로라서 확인용 임시 DB 에도 같은 스니펫을 쓴다.
- 스킬 "대상" 절의 "판정 기록은 `v_repo_latest` 에 있다(점수·근거 인용·요약)"를 바로잡는다. 뷰에는 인용(`evidence`)이 없으므로 "점수·요약은 `v_repo_latest`, 축별 인용은 `judgment.evidence`"로 고친다.

- `weight` 정의: 이슈·토론이면 반응 합계(`reactions.total_count`) + 댓글 수다. 댓글이면 그 댓글의 반응 합계다. README 출처면 0 이다.
- `source_url` 은 인용이 실제로 있는 가장 좁은 위치로 한다. 댓글이면 `#issuecomment-<id>`, README 면 `blob/<sha>/README.md` 다.
- 신호 파일은 `.cache/`(gitignore)에 둔다. 정본은 `export` 한 `data/signal.jsonl` 이다.

### 3.4 인용 대조 — 스크래치 스크립트

신호 파일을 적재하기 전에 인용이 원문에 있는지 확인한다. 공백을 정규화하고 부분 문자열 일치를 본다.

| 출처 | 대조 대상 |
|---|---|
| `…/issues/<n>` · `…/pull/<n>` | `gh api repos/<r>/issues/<n>` 의 제목+본문 |
| `…#issuecomment-<id>` | `gh api repos/<r>/issues/comments/<id>` 의 본문 |
| `…/blob/<ref>/<path>` | `.cache/repos/<owner>__<repo>/<path>` |
| 그 밖(Discussions·외부 웹) | 목록으로 뽑아 메인 세션이 하나씩 열어 확인한다 |

같은 스크립트가 개인정보 형태(이메일·전화번호·키)의 인용도 따로 뽑는다(§7.1). 스크립트는 1차 재현율 점검 스크립트처럼 세션 스크래치에 둔다. 두 번째 주제에서 다시 쓰게 되면 `labbook` 명령으로 승격한다(§7.3).

### 3.5 T 면책 편향 교정 — 노트의 "성과 주장의 신뢰도" 절

판정(`judgment`)은 고치지 않는다(재판정 없음 원칙). 노트에서 T 를 다시 매기고, 그 값을 frontmatter `t_deep` 에 남긴다. 스킬의 조사 항목 "성과 주장의 신뢰도"에 아래 지침을 넣는다.

1. **주장 목록**: README·문서·논문·홈페이지·스크린샷에서 수익률·적중률·샤프·"시장 대비 초과" 같은 성과 주장을 모두 찾는다. 원문을 인용하고 위치를 적는다.
2. **면책 문구는 따로 적는다.** "연구용", "투자 조언 아님"은 성과 주장이 없다는 근거가 아니다. 1번에서 주장이 하나라도 나오면, 면책 문구가 있어도 "성과를 주장하지 않는 도구"(5점)로 보지 않는다.
3. **검증 수단**: 백테스트 기간·종목 수, 수수료·슬리피지, look-ahead·생존 편향 대책, LLM 학습 컷오프 이후 구간, 포워드·페이퍼 기록을 확인한다. 각각 있는지 없는지를 적는다.
4. **판정**: rubric-v1 T 앵커(1·3·5)로 `t_deep` 을 매긴다. 절 끝에 `심층 T n (판정 T m) — 한 줄 사유` 를 적는다. 차이가 2 이상이면 ⚠ 를 붙인다.

frontmatter 예:

```markdown
---
entity: github:tauricresearch/tradingagents
gh_id: 909213664
judged: 2026-09-27  rubric: v1
t_deep: 2
tags: [llm-agent, multi-agent, us-equity]
---
```

`judgment` 가 없는 레포(worldmonitor)는 `judged: -  rubric: -` 로 두고 `t_deep` 만 적는다.

마지막에 전체 노트의 대조표를 만든다. 레포, 판정 T, 심층 T, 차이, 원인(면책 오독·입력 한계·그 밖)을 싣는다. 인계 문서와 PR 본문에 넣는다.

#### 현재 코드

```
변경 없음. .claude/skills/labbook-deep-dive/SKILL.md(§3.2 예산·§3.3 적재·§3.5 지침)와
topics/stock-oss/{notes/, index.md, log.md, reports/funnel-*.md}, data/*.jsonl 만 바뀐다.
```

#### 장점

- 사용자 작업은 표 한 장을 보고 버튼 두 개와 파일럿 버튼 하나를 누르는 것뿐이다.
- 레포마다 컨텍스트를 새로 쓰므로 뒤 레포의 품질이 앞 레포에 밀리지 않는다. 배치 커밋과 노트 유무로 세션이 끊겨도 이어서 할 수 있다.
- DB 쓰기는 메인 세션 한 곳에서만 한다. 동시 쓰기와 따옴표 깨짐이 없다.
- T 교정 결과가 판정을 건드리지 않고 기록으로 남아, 판정 견고성 계획의 입력이 된다.

#### 단점

- 서브에이전트 병렬 실행은 구독 사용량을 한꺼번에 많이 쓴다. 파일럿에서 재고, 한도에 걸리면 배치 크기를 줄인다(§7.1).
- 메인 세션은 서브에이전트가 읽은 원문을 보지 못한다. 검수는 노트 형식과 인용 대조로 한정된다. 내용의 판단(공백·차용할 부분)은 서브에이전트를 믿는다.

## 5. 권장 사항

### 5.1 추천 옵션

후보표 + 버튼 확인(§3.1) → `select --confirm` → `funnel` → 서브에이전트 5개씩 배치로 심층분석(§3.2) → 인용 대조 뒤 적재(§3.3·§3.4) → T 대조표(§3.5).

### 5.2 근거

- 사람 검토를 겸하는 확인은 순위의 타당성을 보는 일이다. 그러려면 이름만이 아니라 점수, 동점, 경계에서 밀린 레포가 보여야 한다. 표 한 장과 버튼 두 개면 사용자 수고가 가장 적다.
- 후보 빼기는 드물 것으로 보고 코드를 고치지 않는다. 확정 뒤 SQL 한 줄과 `--add` 로 충분하다. 빼기가 반복되면 그때 `select --drop` 을 계획한다(§7.3).
- 메인 세션에서 차례로 돌리는 방식(세션당 5개)은 원문을 직접 보고 검수할 수 있다. 하지만 뒤 레포일수록 컨텍스트가 차서 노트 품질이 고르지 않고, 세션이 4개 필요하다. 그래서 쓰지 않는다(2026-09-28 사용자 확정).
- 원 계획은 심층분석을 "대화형 스킬"로 정했다(§5.1). 서브에이전트도 대화형 세션 안의 도구라서 이 결정과 어긋나지 않는다. 판정처럼 `claude -p` 로 격리하는 것이 아니다.
- 가정 1: 사용자 입력은 세 번이다 — `select` 확인 두 문항, 파일럿 게이트 하나.
- 가정 2: 신호 0개인 레포(데이터 라이브러리의 버그 이슈뿐인 경우)도 노트는 쓴다. 신호 수를 채우려고 버그 보고를 `pain` 으로 억지로 넣지 않는다.

- 위험 경로(8·9단계): 신뢰할 수 없는 레포를 clone 하고, 도구를 가진 서브에이전트가 그것을 읽는다. 대응은 스킬 가드레일(실행·바이너리·레포 속 지시 금지)을 서브에이전트 프롬프트에 그대로 넣는 것이다. 메인은 서브에이전트 보고의 "의심 사항"을 검수 때 확인한다. 공개 이슈 인용에 섞인 개인정보는 §7.1 대로 거른다.
- 커밋되는 데이터는 공개 레포 메타데이터, 공개 이슈 원문 인용, 노트뿐이다. LabBook 은 공개 레포다. 인용에 개인정보(이메일·전화번호)가 섞이면 그 신호는 버린다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- 병렬 서브에이전트가 구독 한도에 걸린다. / 대응: 파일럿에서 배치 소요를 잰다. 한도에 걸리면 끝난 노트만 검수·커밋하고, 리셋 뒤 배치 크기를 3으로 줄여 이어서 한다. 남은 레포는 노트 유무로 가린다.
- 서브에이전트가 레포 속 지시(README 인젝션)를 따르거나 스크립트를 실행한다. / 대응: 프롬프트 가드레일, 검수 때 보고의 의심 사항 확인. 노트에 레포 텍스트의 지시문이 그대로 옮겨졌으면 그 절을 다시 쓴다.
- 공개 이슈 인용에 개인정보(이메일·전화번호·계좌번호·API 키)가 섞여 공개 레포에 커밋된다. / 대응: 인용 대조 스크립트가 이메일·전화번호·키 형태의 정규식에 걸리는 신호를 따로 뽑는다. 메인이 그 신호를 버리거나 해당 부분을 뺀 구절로 줄인다. 줄인 구절도 원문의 연속된 부분이어야 한다. 노트 본문도 같은 기준으로 확인한다.
- 인용이 번역·요약으로 바뀐다(특히 cn 레포의 중국어 이슈). / 대응: 인용 대조가 걸러 낸다. 인용은 원어 그대로 두고, 노트 본문에서만 한글로 풀어 쓴다.
- 큰 레포(openbb 등)는 clone 이 크고 느리다. / 대응: `--depth 1` 을 유지한다. 코드는 구조 파악에 필요한 만큼만 읽는다(예산은 이슈·포크에만 둔다). `.cache/repos/` 는 gitignore 다.
- `gh search issues` 는 반응순 정렬 결과가 1,000건까지만 나온다. 이슈가 아주 많은 레포(yfinance)는 오래된 인기 이슈 위주로 보인다. / 대응: 상위 30개면 충분하다. 최근 수요는 댓글순 30개로 보완한다.
- 심층 T 도 Claude 판단이다. / 대응: 대조표는 판정기와 사람이 맞는지 보는 증거가 아니다. 입력을 늘리고(원문·문서 전체) 지침을 바꿨을 때 판정이 얼마나 달라지는지 보는 증거로만 쓴다. 판정 견고성 계획에서 그렇게 인용한다.

### 7.2 의존성

- `gh`(github.com 로그인), `git`, Claude Code Agent 도구(서브에이전트)·WebSearch, Python 3.14, `sqlite3`.
- 브레인스토밍(다음 조각)은 이번 산출물(`signal`·노트)을 입력으로 쓴다. 판정일은 2026-10-24 다.
- 하네스: 1·2차에 이어 세 번째 "운영 실행 계획"(TDD 대신 확인 열, 사용자 게이트 행)이다. 이번에는 "서브에이전트 배치 + 파일럿 게이트" 행 형식도 새로 썼다. indie-forge 에 운영 실행 계획 형식을 제안할 근거에 이 사례를 더한다.

### 7.3 범위 밖 / 향후 작업

- 브레인스토밍·원페이저·`toolkit.md`(원 순번 12): 다음 조각.
- `select --drop`(빼고 다음 순위로 자동 채움): 빼기가 반복될 때 계획한다.
- 인용 대조를 `labbook` 명령으로 승격: 두 번째 주제에서 다시 쓰게 되면 한다.
- `idouble` error 재시도, T 루브릭 개정과 재판정 경로: 판정 견고성 계획(인계 §3.0-3). 이번 T 대조표가 입력이다.
- 레포 실제 구동(툴킷 상위의 로컬 실행): 원 계획 §7.3 그대로, 툴킷 작성 때 필요하면 개별로 한다.
