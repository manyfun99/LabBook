### 1.2 문제점

- 문제 1 — **골드의 의미가 바뀌었다.** 원 계획은 사용자가 골드를 채점하기로 했지만, 실제로는 Claude 가 채점했다(인계 §2, 2026-09-27 사용자 결정). 판정기(opus)와 같은 계열이다. 그래서 일치율 70% 는 "사람과 맞는다"는 뜻이 아니다. "README·이슈를 깊게 읽은 판단을 얕은 입력으로 재현한다"는 뜻일 뿐이다.
  - 원 계획의 보정 실패 대응은 "다중 계열 API 판정 재검토"(§5.2 기각 대안 2·§7.1)다. 이 대응은 사람 기준에서 벗어나는 단일 모델 편향을 줄이려는 것이다. 골드가 Claude 채점이면 다른 계열 판정을 Claude 골드에 맞춰 보는 셈이 되어 의미가 없다.
- 문제 2 — **±1 기준이 느슨한 축이 있다.** T 는 골드 절반(10개)이 5점("성과 주장 없는 도구")이다. 판정기도 5를 주기 쉬운 부류라서 일치율이 구조적으로 높게 나온다. 5점 척도에서 ±1 은 무작위로도 약 50% 가 맞는다. 70% 만 보면 축의 약점이 가려질 수 있다.
- 문제 3 — **입력 차이는 루브릭을 고쳐도 좁혀지지 않는다.** 골드 메모에는 이슈 내용이 근거로 들어 있다(예: "논문 성과가 재현 안 된다는 이슈", "Pro 버전·대기자 요청 이슈"). 판정기는 이슈 제목만 본다. 이런 차이를 루브릭 문구로 맞추면 20개에 과적합된다.
- 문제 4 — **조정 이력이 남지 않는다.** `gold-v1.md` 는 덮어쓰기다. 어떤 조정이 일치율을 어떻게 바꿨는지 비교할 수 없다.
- 문제 5 — **error 재시도에 상한이 없다.** 1차와 같은 구조다. 계속 실패하는 레포가 있으면 대기열이 0 이 되지 않는다. 또 구독 한도에 걸린 뒤에도 실행을 계속하면, 남은 레포가 모두 빠르게 `error` 로 바뀐다.
- 문제 6 — **소요를 모른다.** 레포당 opus 1회이고 입력은 최대 약 3만 자다. 430개가 몇 시간인지, 구독 한도로 하루에 몇 개를 돌릴 수 있는지 실측값이 없다.

## 2. 목표

### 2.1 달성 목표

- `judge --gold` 로 판정기와 골드를 비교한다. 체계적 차이만 루브릭에 반영한다. 조정 횟수에는 상한을 둔다. 그다음 rubric-v1 을 확정한다.
- 대기열 430개 전부를 정밀 판정하고 `data/*.jsonl` 로 커밋한다.
- 다음 조각(`funnel`·`select`)이 바로 시작할 수 있게 인계 문서를 갱신한다.

### 2.2 성공 기준

- **확정 게이트** (원 계획 §2.2 수치 유지, 의미는 재정의 — 2026-09-27 사용자 확정): 채택 회차(§3.2) `gold-v1.md` 의 축별 ±1 일치율이 P·I·N·T **각각** 70% 이상이다. 이 수치는 "깊은 판단과 얕은 입력 판정의 일치"로 기록한다. 사람 기준 보정이라고 쓰지 않는다.
- 보조 기록 (게이트 아님): 축별 ⚠(차이 >1) 건수와, ⚠ 마다 원인 분류(§3.2). T 축의 경우 골드 5점 10개를 뺀 나머지의 일치 수도 따로 적는다(문제 2).
- 사람 확인은 이번 조각에서 추가하지 않는다. 다음 조각의 `select` 확인 단계가 그 역할을 한다. 사용자가 P·I 상위 후보 목록을 보고 이상한 것을 고르게 한다. 순위의 타당성을 보는 것이라, 절대점수를 채점하는 것보다 부담이 작다.
- 조정은 최대 2회다(골드 실행 최대 3회, 2026-09-27 사용자 확정). 조정할 때마다 `rubric-v1.md` 와 `gold-v1.md` 를 함께 커밋해 이력을 남긴다.
- 전수 판정: 대기열 430개가 모두 `judgment(full)` 을 갖는다. 예외는 재시도 상한(§3.4) 뒤에도 남은 `error` 뿐이고, 그 레포와 `reason` 을 인계 문서와 PR 본문에 적는다.
- 자기 일치 (기록만): 골드 레포 19개의 전수 판정 점수와 채택 회차(§3.2) `--gold` 의 LLM 점수를 비교한다. 루브릭은 같다. 입력은 거의 같다: README 는 7일 캐시라 그 안이면 같고(`github.py:136`), 이슈는 매번 새로 조회해서 댓글 수·순위가 조금 바뀔 수 있다(`github.py:153`). 그래서 차이는 대부분 판정기의 비결정성으로 본다. 축별 ±1 일치율을 기록한다. 전수 판정이 채택 회차 `--gold` 에서 7일을 넘겨 도는 레포는 README 가 바뀌었을 수 있다고 함께 적는다.
- `data/*.jsonl` 을 커밋하고, 빈 DB 에 `import` 해서 행 수가 같은지 확인한다.
- 전체 테스트 135개가 통과한다(코드 무변경 회귀).

## 3. 해결 방안

### 3.1 골드 실행과 소요 실측

```
time python3 -m labbook judge stock-oss --gold   # 백그라운드, 로그는 스크래치에
```

- 20회 호출의 총 소요로 레포당 평균을 잰다. 430 × 평균으로 전수 소요를 추정한다(§3.4).
- `--gold` 는 실패한 레포의 이름만 리포트에 적고 사유는 출력하지 않는다(`judge.py:gold` 의 `except` 가 이름만 담는다). 그래서 실패가 1건이라도 있으면 아래처럼 구독 한도 탓인지 가린다. 확인 호출은 `echo ok | claude -p --model opus` 이다.
  - 확인 호출이 한도 메시지로 실패한다 → 이번 실행은 게이트 판정에 쓰지 않는다. 리셋 뒤에 20개 전체를 다시 돌린다.
  - 확인 호출이 성공한다 → 한도 외 실패로 본다. 실패한 레포 이름을 기록하고(사유 불명), 나머지 레포의 일치율로 게이트를 판정한다. 실패가 3개 이상이면(표본 17개 미만) 게이트 판정을 보류한다. 실패한 레포 이름을 보여 주고, 버튼으로 둘 중 하나를 고르게 한다: "20개 전체 재실행"(이 회차는 조정 횟수에 넣지 않는다) 또는 "남은 표본으로 게이트 판정".

### 3.2 ⚠ 원인 분류와 조정 규칙

⚠ 행마다 `gold-v1.md` 의 LLM 근거와 골드 `note` 를 대조해 원인을 하나로 분류한다.

| 원인 | 판별 | 조치 |
|---|---|---|
| 루브릭 모호 | 같은 입력으로 앵커를 다르게 읽었다(예: "유료 데이터 필수"의 범위, "성과를 주장하지 않는 도구"의 경계) | 앵커·정의 문구를 고친다 |
| 입력 한계 | 골드 근거가 이슈 본문이나 README 30,000자 뒤에 있다. 판정기 입력에는 없다 | 루브릭은 고치지 않는다. 기록만 한다(§7.3) |
| 골드 판단 차이 | 입력에 근거가 있고 앵커도 분명한데 골드와 판정기가 다르게 봤다 | 루브릭도 골드도 고치지 않는다. 기록만 한다 |

과적합 방지 규칙:
- 같은 원인·같은 방향의 ⚠ 가 **2개 레포 이상**일 때만 루브릭을 고친다. 레포 하나만 맞추는 조정은 하지 않는다.
- 루브릭에 레포 이름이나 특정 레포 전용 규칙을 넣지 않는다. 앵커·정의·"판정하는 사람의 맥락"만 고친다.
- 골드(`gold.jsonl`)는 고치지 않는다. 판정기에 맞춰 골드를 바꾸면 게이트가 무의미해진다.
- 되돌림 규칙은 두지 않는다. 대신 **최선 회차를 채택한다**(2026-09-27 사용자 확정). 판정기가 비결정적이라, 레포 하나가 새로 ⚠ 가 됐다고 조정이 나빴다고 볼 수 없기 때문이다.
  - 채택 기준: 게이트에 쓸 수 있는 골드 회차(§3.1) 중 **최저 축 일치율이 가장 높은 회차**의 루브릭을 v1 으로 확정한다. 같으면 전체 일치율이 높은 회차, 그것도 같으면 나중 회차를 고른다.
  - 채택 회차가 마지막 회차가 아니면 다시 돌리지 않는다. 그 회차 커밋의 두 파일을 복원해서 커밋한다: `git checkout <커밋> -- topics/stock-oss/rubric-v1.md topics/stock-oss/reports/gold-v1.md`, 메시지는 `docs(stock-oss): 골드 보정 N회차 채택`.
  - 게이트 판정(§3.3)과 자기 일치 비교(§2.2)는 채택 회차의 `gold-v1.md` 를 기준으로 한다.

이력 보존: 파일명을 바꾸거나 코드를 고치지 않는다. 골드 실행마다 `rubric-v1.md` 와 `reports/gold-v1.md` 를 한 커밋에 넣는다. 커밋 메시지에 회차와 축별 일치율을 적는다. 예: `docs(stock-oss): 골드 보정 1회차 — P 75% · I 65% · N 85% · T 90%`. 회차끼리는 `git log -p topics/stock-oss/reports/gold-v1.md` 로 비교한다.

### 3.3 게이트 판정과 실패 대응

| 결과 | 다음 |
|---|---|
| 이번 회차 4축 모두 70% 이상 | 최선 회차 채택(§3.2) → rubric-v1 확정 → 전수 판정(§3.4) |
| 미달, 조정 여지 있음(같은 원인·같은 방향의 "루브릭 모호"가 2개 레포 이상), 조정 2회 미만 | 조정 → 골드 재실행 |
| 미달, 그리고 위 행이 아닌 모든 경우(조정 2회를 다 썼거나, 조정 여지가 없음 — "루브릭 모호"가 1개 레포 이하이고 나머지는 입력 한계·골드 판단 차이) | 최선 회차를 채택한다(§3.2). 채택 회차도 미달이면 **전수 판정을 시작하지 않는다.** 축별 원인 분류표를 사용자에게 보여 주고, 아래 셋 중 하나를 버튼으로 고르게 한다. 자동으로 진행하지 않는다(2026-09-27 사용자 확정) |

미달일 때의 선택지:

| 선택지 | 내용 | 비용 |
|---|---|---|
| A. 그대로 진행(권장) | 미달 축은 인계 문서와 퍼널에 "참고용"으로 표시한다. `select` 에서 그 축의 상위 후보를 사용자가 더 꼼꼼히 확인한다 | 없음 |
| B. 입력 보강 | 이슈 본문 일부를 입력에 넣는 코드를 고친다. 별도 계획으로 한다 | 계획 1개 + 골드 재실행 |
| C. 다중 계열 판정 | 원 계획 §5.2 기각 대안 2. 골드가 Claude 채점이라 이 조각에서는 권하지 않는다(문제 1) | API 키·종량 과금 |

원 계획 §7.1 의 "보정 실패면 다중 계열 재검토"는 이 표의 C 로 대신한다. 사람이 채점한 골드가 생기기 전까지는 C 를 기본 대응으로 두지 않는다.

### 3.4 전수 판정 분할·재시도 상한

```
python3 -m labbook judge stock-oss --limit 50    # 백그라운드, 회차마다 아래 SQL 로 상태 확인
```

- 소요 추정: 레포당 평균(§3.1) × 430. 참고로 평균이 90초면 약 11시간이다.
- 하루 처리량: 첫 회차 `--limit 50` 에서 한도에 걸리는지 본다. 걸리지 않으면 한도가 리셋될 때마다 50개씩 이어 간다. 걸리면 그 회차에서 처리된 수를 한 한도 창의 처리량으로 본다. 일정(예상 완료일)은 첫날 실측 뒤 사용자에게 한 줄로 알린다.
- 진행 감시: `judge` 는 끝날 때만 출력한다. 그래서 회차 중에는 아래 상태 SQL 과 최근 `error` 사유 SQL 을 몇 분마다 읽는다. 읽기는 판정 중에도 안전하다. 레거시 트랜잭션 모드라 트랜잭션이 첫 INSERT 에서 시작되고, LLM 호출 동안에는 잠금을 잡지 않는다(`db.py:connect`, `judge.py:judge`). "DB 에 쓰는 명령을 동시에 돌리지 않는다"(인계 §4)는 규칙은 그대로 지킨다.
- 한도 대응: 회차 중에 `error` 가 연속으로 늘고, `reason` 에 limit·usage 같은 한도 문구가 있으면 즉시 멈춘다(프로세스 종료). 레포 단위로 커밋되므로 끝난 것은 남는다.
- 재시도 거동 (코드 무변경, 2026-09-27 사용자 확정): 대기열이 `ORDER BY e.id` 이고 `error` 레포도 포함한다. 그래서 `error` 레포는 다음 `--limit 50` 회차 맨 앞에서 자동으로 재시도된다. 이 자동 재시도는 받아들인다. 1차 1단 선별에서 `error` 가 0건이었으므로 드물다고 본다.
  - 같은 사유(한도 외)로 두 회차 연속 실패한 레포는 레포·`reason` 을 스크래치에 적어 둔다.
  - 신규 대기(판정 이력이 없는 레포)가 0 이 되면 `error` 만 남는다. 이 상태에서 최대 2회 더 돌리고, 그래도 남은 `error` 는 멈추고 기록한다. 한도 때문에 생긴 `error` 가 남아 있으면, 리셋 뒤에 돌린 회차만 이 2회에 센다.

```sql
-- 최근 error 사유 (한도 여부 판별)
SELECT e.key, jd.reason, jd.decided_at FROM screening jd JOIN entity e ON e.id = jd.entity_id
WHERE jd.topic = 'stock-oss' AND jd.stage = 'judged' AND jd.decision = 'error'
ORDER BY jd.decided_at DESC LIMIT 10;
```
- 회차마다 `export` → 커밋한다(`chore(stock-oss): 정밀 판정 N/430`). 세션이 끊겨도 진행분이 git 에 남는다.

```sql
-- 대기열 상태: 신규 대기 · error 대기 · 완료
SELECT
  SUM(j.id IS NULL AND jd.decision IS NULL)      AS 신규,
  SUM(j.id IS NULL AND jd.decision = 'error')    AS error,
  SUM(j.id IS NOT NULL)                          AS 완료
FROM screening tr
JOIN screening sc ON sc.entity_id = tr.entity_id AND sc.topic = tr.topic AND sc.stage = 'scoped' AND sc.decision = 'include'
LEFT JOIN screening jd ON jd.entity_id = tr.entity_id AND jd.topic = tr.topic AND jd.stage = 'judged'
LEFT JOIN judgment j ON j.entity_id = tr.entity_id AND j.topic = tr.topic AND j.stage = 'full'
WHERE tr.topic = 'stock-oss' AND tr.stage = 'triaged' AND tr.decision IN ('include', 'unsure');
```

## 5. 권장 사항

### 5.1 추천 옵션

골드 실행 → ⚠ 원인 분류 → 조건부 조정(최대 2회) → 게이트 → 전수 판정(`--limit 50` 회차, 재시도 상한 2회) 순으로 진행한다. 코드는 바꾸지 않는다.

### 5.2 근거

- 70% 수치는 원 계획의 합의이므로 유지한다. 골드 채점자가 바뀐 것은 기준의 의미를 재정의해서 반영한다. 기준을 올리거나 새 지표를 게이트로 만들면 20개 표본에서 근거 없이 문턱만 바뀐다.
- 다중 계열 판정(C)은 사람 골드가 있을 때 의미가 있다(문제 1). 미달이면 멈추고 묻되, 권장안은 A 다. 사용자 수고가 가장 적고(`prefer-minimal-actionable`), `select` 확인이 사람 검토 역할을 한다.
- 가정 1: 이번 조각에서 사용자 입력은 세 경우뿐이다: 골드 실패 3개 이상(§3.1), 게이트 미달(§3.3), 첫날 소요 알림(§3.4, 답을 받지 않는다). 통과하면 사용자 작업 없이 끝까지 간다.
- 가정 2: 판정을 여러 날에 걸쳐 돌려도 README 캐시(7일)가 만료되기 전에 끝난다. 만료되더라도 README 를 다시 받을 뿐이라 결과에는 해가 없다. `input_sha` 는 판정 시점의 값으로 남는다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- 구독 한도가 예상보다 작아 전수 판정이 여러 날 걸린다. / 대응: `--limit 50` 회차와 레포 단위 커밋으로 이어서 돌린다. 첫날 실측 뒤 일정을 알린다.
- 한도에 걸린 회차에서 남은 레포가 `error` 로 쌓인다. / 대응: 연속 `error` 를 보면 즉시 멈춘다. 이 `error` 는 재시도 횟수에 넣지 않는다. `error` 여도 `judgment` 행이 없으니 다음 실행에 다시 들어간다.
- 판정기가 비결정적이라 같은 루브릭으로도 골드 실행마다 일치율이 흔들린다. / 대응: 레포 하나의 변화로 조정을 되돌리지 않고, 회차 전체로 비교해 최선 회차를 채택한다(§3.2). 자기 일치 수치로 흔들림의 크기를 기록한다.
- 루브릭을 확정한 뒤 문제가 보여도 재판정 경로가 없다(UNIQUE). / 대응: 확정 전에 골드로 충분히 본다. 재판정은 원 계획 §7.3 범위 밖 그대로 둔다. 필요하면 별도 계획으로 한다.
- 인용 검사 실패가 특정 레포(README 가 거의 비었거나 이미지뿐인 레포)에서 반복된다. / 대응: 재시도 상한 뒤 남은 `error` 로 기록한다. 루브릭의 "근거가 부족하면 그 사실을 보여 주는 문장을 인용" 규칙이 먹히지 않는 사례로 모아 둔다.

### 7.2 의존성

- `gh`(github.com 로그인), `claude` CLI 로그인 세션(opus 사용 가능한 구독), Python 3.14, `sqlite3`.
- PR #3 머지 여부(브랜치 기점만 달라진다).
- 하네스: 1차에 이어 코드 변경 없는 운영 실행 계획이다. 6장 확인 열 형식을 다시 썼다. 두 번째 사례이므로 indie-forge 에 "운영 실행 계획" 형식(TDD 대신 확인 열, 사용자 게이트 행)을 제안할 근거가 모였다.

### 7.3 범위 밖 / 향후 작업

- `funnel`·`select`·심층분석·브레인스토밍(원 순번 10~12): 다음 조각. `select` 확인이 이번 게이트의 사람 검토를 겸한다.
- 판정 입력에 이슈 본문 넣기: ⚠ 원인이 "입력 한계"로 여럿 모이면 선택지 B 로 별도 계획한다.
- 사람 채점 골드(부분이라도)와 다중 계열 판정: 사람 기준 보정이 필요해질 때 한다.
- 1단 exclude 된 사용자 스타(worldmonitor)의 정밀 판정: 재판정 없음 원칙 때문에 하지 않는다. `select --add` 로 심층분석에 넣을 수 있다.
