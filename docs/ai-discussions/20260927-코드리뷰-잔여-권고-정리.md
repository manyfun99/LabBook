### 1.2 문제점

- 문제 1 — 테스트 공백 3건
  - `tests/test_github.py` 는 `GitHub.truncated` 가 채워지는 것만 본다. `collect()` 가 이를 요약에 넘기는지, `cli` 가 경고를 찍고 `log.md` 에 "잘린 검색 N" 을 남기는지는 테스트가 없다. `cli.py` 는 테스트 파일이 아예 없다.
  - `_triage_batch` 에서 묶음의 모든 레포가 GitHub 오류면 LLM 을 부르지 않고 돌아가는 분기가 테스트되지 않는다. 이 분기가 빠지면 빈 `<repo>` 목록으로 sonnet 을 부른다.
  - `test_폴백_창은_N일부터_N_7일_전까지다` 는 창 안·밖 스냅샷이 함께 있을 때 창 안을 고르는지만 본다. 창 밖 스냅샷만 있을 때 `None` 인지(하한 `lo`)는 단언하지 않아, `BETWEEN lo AND hi` 가 `<= hi` 로 바뀌어도 통과한다.
- 문제 2 — `FakeLLM` 이 `run_claude` 의 재시도·검증 규칙을 따로 구현한다. 실제 `run_claude` 의 규칙(시도 횟수, `ValueError` 만 검증 실패로 잡음, 모델 ID 추출)이 바뀌어도 판정 테스트는 계속 통과한다. `test_지어낸_인용은_재시도하고…` 같은 테스트가 재시도를 검증한다고 적혀 있지만 실제로는 대역의 재시도를 본다.
- 문제 3 — 중복 두 가지
  - screening upsert SQL 이 두 모듈에 복제돼 있다. 한쪽만 고치면(예: `sources` 보존) 단계마다 거동이 갈린다.
  - gh_id 로 레포 메타를 조회하는 식이 세 곳에 있다. `GitHub.repo(full_name)` 에 대응하는 메서드가 없다.
- 문제 4 — `_suspects` 가 범위 내 레포마다 스냅샷 1회 + 판정 1회를 조회한다(800개면 약 1,600쿼리). 지금 규모에서는 느리지 않지만 롱테일(§7.3, +2,500개)을 넣으면 커진다.

#### (2) `FakeLLM` 을 실제 `run_claude` 위에 올린다

현재 코드

        self.prompts.append((prompt, model))
        last = None
        for attempt in range(2):          # run_claude 의 재시도를 따로 구현
            out = self.responder(prompt, attempt)
            ...
        raise LLMError(str(last))

개선 코드

```python
class FakeLLM:
    """실제 run_claude 에 가짜 claude 프로세스를 물린다 — 재시도·검증·모델 ID 규칙은 llm.py 것을 그대로 탄다."""

    def __init__(self, responder):
        self.responder = responder
        self.prompts = []   # llm_call 단위 (재시도는 세지 않는다)
        self.runs = 0       # 프로세스 호출 단위

    def __call__(self, prompt, schema, model, *, validate=None):
        self.prompts.append((prompt, model))
        attempts = iter(range(llm.ATTEMPTS))

        def runner(args, *, input, **kwargs):
            self.runs += 1
            out = self.responder(input, next(attempts))
            if isinstance(out, Exception):
                return subprocess.CompletedProcess(args, 1, stdout="", stderr=str(out))
            body = {"is_error": False, "structured_output": out,
                    "modelUsage": {f"model-{model}": {"outputTokens": 1}}}
            return subprocess.CompletedProcess(args, 0, stdout=json.dumps(body), stderr="")

        return llm.run_claude(prompt, schema, model, validate=validate, runner=runner,
                              cwd=Path(tempfile.gettempdir()))  # 이미 있는 디렉터리 — mkdir 부작용 없음
```

- responder 시그니처 `(prompt, attempt)` 와 `prompts`·`"model-{model}"` 은 그대로라 기존 테스트 단언을 고치지 않는다. 모델 ID 는 `_used_model` 이 별칭(`opus`) 이 든 키 `model-opus` 를 고른다.
- 추가 테스트: `test_지어낸_인용은_재시도하고…` 에 `llm.runs == llm.ATTEMPTS` 단언을 더한다.

#### (3) 중복 정리

```python
# labbook/db.py
def set_screening(conn, topic, entity_id, stage, decision, reason):
    """단계 판정 upsert — scoped 는 refresh 마다, triaged·judged 는 error 재시도 때 덮어쓴다."""
    conn.execute(
        "INSERT INTO screening (topic, entity_id, stage, decision, reason, decided_at) VALUES (?, ?, ?, ?, ?, ?) "
        "ON CONFLICT (topic, entity_id, stage) DO UPDATE SET decision = excluded.decision, reason = excluded.reason, "
        "decided_at = excluded.decided_at",
        (topic, entity_id, stage, decision, reason, utc_now()))

# labbook/github.py
def repo_by_id(self, gh_id):
    """gh_id 로 조회 — 이름 변경에 강하고, 삭제된 레포의 이름을 다른 레포가 쓰는 경우에도 엉뚱한 레포를 보지 않는다."""
    return normalize_repo(self.get(f"repositories/{gh_id}"))
```

- `metrics._set_scope`·`judge._set_screening` 을 지우고 호출처를 `set_screening(…, "scoped", …)` 등으로 바꾼다.
- `metrics._take_snapshot`·`judge._triage_batch`·`judge.judge` 는 `gh.repo_by_id(row["gh_id"])` 를 쓴다. `_take_snapshot` 의 gh_id 조회 이유 주석은 새 메서드 docstring 으로 옮긴다.
- 테스트 대역(`test_judge.FakeGH`, `test_metrics.FakeGH`)은 `repo_by_id = GitHub.repo_by_id` 로 실제 메서드를 빌려 쓴다. 대역의 `get` 경로 기록이 그대로라 `test_gh_id로_조회한다` 가 바뀌지 않는다.
- `collect.add_source`(sources 누적)와 `report.select`(`DO NOTHING`)의 screening 쓰기는 의미가 달라 합치지 않는다.

#### (4) 의심 집계를 두 쿼리로

현재 코드: 범위 내 레포마다 스냅샷·판정을 각각 조회 (`report.py:_suspects`).

개선 코드

```python
def _suspects(conn, topic, included):
    """범위 내 레포 중 최신 스냅샷 플래그나 판정 증거(인젝션·바이너리 링크)가 선 것."""
    flagged = {r[0] for r in conn.execute(
        "SELECT s.entity_id FROM snapshot s "
        "WHERE s.taken_at = (SELECT MAX(taken_at) FROM snapshot WHERE entity_id = s.entity_id) "
        "AND json_array_length(COALESCE(s.flags, '[]')) > 0")}
    flagged |= {r[0] for r in conn.execute(
        "SELECT entity_id FROM judgment WHERE topic = ? "
        "AND (json_extract(evidence, '$.injection_suspect') OR json_extract(evidence, '$.binary_link'))", (topic,))}
    return len(flagged & included)
```

- 판정 기준은 이전과 같다: 최신 스냅샷만 보고, 판정 증거는 triage·full 두 단계 모두 본다. SQLite 3.53 은 JSON 함수가 내장이다(`v_repo_latest` 가 이미 `json_extract` 를 쓴다).
- 교체 전에 특성 테스트를 먼저 넣는다: triage 판정의 `binary_link` 만 선 레포는 센다, 옛 스냅샷에만 플래그가 있으면 세지 않는다, 범위 밖 레포는 세지 않는다, 레포 1개·20개일 때 SQL 문 수가 같다.

#### 장점

- 판정 테스트가 실제 재시도 경로를 검증한다. `llm.py` 를 바꾸면 판정 테스트도 반응한다.
- upsert·레포 조회의 수정 지점이 하나가 된다.
- 동작이 바뀌지 않으므로 조사 실행(인계 §3)을 기다리게 하지 않는다.

#### 단점

- `test_cli.py` 는 `cli.ROOT`·`cli.GitHub` 를 패치해야 한다. `cli` 가 경로·어댑터를 주입받지 않는 구조라서다. 구조를 바꾸면 범위가 커지므로 패치로 둔다.
- 대역이 `llm.ATTEMPTS`·`run_claude` 의 `runner` 인자 규약에 묶인다(그게 목적이다).

## 5. 권장 사항

### 5.1 추천 옵션

3.1 을 한 PR 로 진행한다. 순서: 테스트 공백 → 대역 교체 → 중복 정리 → N+1.

### 5.2 근거

- 네 항목 모두 작고 서로 맞물린다(대역 교체 뒤라야 `set_screening`·`repo_by_id` 리팩토링을 실제 경로로 검증할 수 있다). PR 을 나눌 이유가 없다.
- 1회차 조사가 아직 돌지 않아 DB·`data/*.jsonl` 이 없다. 동작 보존 리팩토링을 하기에 가장 싼 시점이다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- 대역 교체 때 기존 테스트가 대역의 우연한 거동에 기대고 있었을 수 있다(예: 재시도 횟수, 모델 ID 형식). / 대응: 단언은 고치지 않는 것을 원칙으로 하고, 깨지는 테스트가 있으면 그것이 실제 `run_claude` 와 어긋나 있던 지점이므로 원인을 PR 본문에 적는다.
- `_suspects` 쿼리 교체로 집계가 달라질 수 있다(`flags` 가 `NULL`, `evidence` 가 `NULL`). / 대응: `COALESCE`·`json_extract` 의 NULL 거동을 특성 테스트로 먼저 고정한다.
- 레포 룰 게이트: DB 스키마·환경변수·API 계약(CLI 출력)·외부 서비스 거동 모두 변경 없음. `repo_by_id` 는 같은 엔드포인트를 같은 방식으로 부른다.
