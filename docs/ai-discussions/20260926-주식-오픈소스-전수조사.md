# 주식투자 오픈소스 전수조사 — 수집·판정 파이프라인과 조사 기록 체계

GitHub 의 주식·투자·AI 트레이딩 오픈소스를 전수조사한다. 결과를 요약·점수화하고, 상위권을 심층분석해 **(1) 내 투자에 쓸 도구**와 **(2) 인디해커 아이템**을 뽑는다. 이 문서는 LabBook 의 첫 조사 주제이면서 **여러 주제에 재활용할 조사 기록 체계**의 첫 설계다.

표기: **[실측]** 2026-09-26 직접 호출 / **[문서]** 논문·공식 문서 / **[추정]** 판단. 근거 조사는 이 세션에서 네 갈래(데이터 소스 실측, 방법론 문헌, 지형 예비 스캔, 기록 관리 동향)로 했다. 원자료 스크립트는 세션 스크래치패드에만 있으므로, 필요하면 다시 수집한다.

## 1. 현황 분석

### 1.1 현재 상태

- 신규. 레포에는 `CLAUDE.md`, `.claude/settings.json`(indie-forge 하네스)만 있다.
- 인접 자산: `~/Workspace/Indy/GuruNote`. 한국 투자자 대상 해외 대가(13F) 한국어 알림 서비스이고, 운영 중이다. 자산은 SEC 수집·텔레그램 봇·`claude -p` 헤드리스 가공 패턴이다. 경쟁·규제 조사는 `GuruNote/docs/ai-discussions/20260923-사전조사-경쟁-시장.md`, `20260926-아이디어-관심기업-공시-알림.md` 에 있다. 이 조사를 브레인스토밍의 입력(기존 경쟁자·규제)으로 쓴다.
- 사용자 GitHub 스타 중 금융 관련 12개: ai-hedge-fund, TradingAgents, Vibe-Trading, AI-Trader, prism-insight, auto-researchtrading, QuantHarness, Kronos, MiroFish, financial-datasets/mcp-server, FinanceDataReader, worldmonitor. **7/12 가 LLM 에이전트 축에 몰려 있다.**

### 1.2 문제점 (원점 검토에서 드러난 것)

- **문제 1 — "스타 수 = 가치"가 성립하지 않는다.**
  - 스타 50 이상 레포의 15.8% 가 가짜 스타 캠페인에 연루됐고, 크립토 봇류에서 흔하다 [문서: StarScout, arXiv 2412.13459].
  - 예비 스캔의 최근 30일 금융 키워드 상위 20개 중 3개가 위장 악성 레포였고, 셋 다 이미 삭제됐다 [실측].
  - `topic:quantitative-finance` 9,132개 중 5,777개가 2026-03 이후 생성이고, 그중 3,972개가 0스타다 [실측]. AI 생성 스팸이 많다는 뜻이다.
- **문제 2 — 라이징 측정 수단이 바뀌었다.**
  - stargazers 목록 API 는 2026-06-30 부터 admin 전용이다. 인증 호출도 404 가 난다 [실측].
  - 이벤트 기반 소스도 믿기 어렵다. OSS Insight 는 2026-03 이후 캡처율 0.3% 라고 스스로 밝히고, ClickHouse github_events 는 월별 공백이 크다 [실측].
  - 대신 2026-09-04 신설된 `GET /repos/{o}/{r}/stargazers/history` 가 동작한다. 주·일 단위이고 합계가 실제 스타 수와 일치한다 [실측].
- **문제 3 — AI 투자 에이전트의 성과 주장을 그대로 믿으면 안 된다.**
  - 20년·100종목 이상으로 넓히면 LLM 전략의 우위가 크게 약해진다 [문서: FINSABER 2505.07078].
  - LLM 은 컷오프 이전 가격을 기억해서, 백테스트가 오염된다 [문서: 2504.14765].
  - 오염 없는 구간에서는 단순 기준선을 이기는 경우가 드물다 [문서: StockBench 2510.02209, LiveTradeBench 2511.03628].
  - → "매매시점 제시"는 개인 활용에서도, 아이템 설계에서도 검증 대상이지 전제가 아니다.
- **문제 4 — LLM 브레인스토밍은 쏠린다.**
  - 시드 아이디어 4,000개 중 중복이 아닌 것은 5% 였다 [문서: Si et al. 2409.04109].
  - 모델을 여러 개 섞어도 서로 비슷하다 [문서: Artificial Hivemind 2510.22954].
  - LLM 아이디어는 실행해 보면 평가가 크게 떨어진다(−1.98) [문서: 2506.20803].
  - → 레포 목록에서 바로 아이디어를 뽑으면 흔한 아이디어로 수렴한다. **수요 신호**(이슈·요청)와 **나만의 자산·제약**을 입력으로 강제해야 한다.
- **문제 5 — 규모.**
  - 금융 관련 ≥100★ 는 약 3,000~3,500개, ≥1000★ 는 약 450~550개다. 백테스트·퀀트 축이 약 1,500개로 가장 크다 [실측+추정].
  - 전부를 LLM 으로 깊게 읽으면 비용이 과하다. 단계별로 걸러야 한다.
- **문제 6 — 한 번 쓰고 버리는 조사가 되기 쉽다.**
  - 조사 결과가 대화나 문서에만 남으면 다음 조사에서 재조회할 수 없다.
  - LabBook 은 여러 주제를 쌓아 교차 인사이트를 얻는 것이 목적이다. 그러니 기록 구조가 주제를 넘어 재사용돼야 한다(사용자 추가 요청).

## 2. 목표

### 2.1 달성 목표

- 목표 1: "유명(≥1000★) + 라이징 + 한국 시장 + 사용자 스타"를 빠짐없이 모으고, 한 번 판정한 레포는 다시 판정하지 않는 **증분 수집·판정 도구**를 만든다.
- 목표 2: 기계 지표(인기·추세·건강·의심) → LLM 선별 → LLM 정밀 판정 → 심층분석으로 좁히는 **4단 퍼널**을 운영하고, 단계별 판정과 **제외 사유**를 남긴다.
- 목표 3: 심층분석에서 **수요 신호**(이슈·요청·불만)를 표준 형태로 기록하고, 이를 입력으로 브레인스토밍해 **아이템 원페이저**와 **개인 투자 툴킷**을 낸다.
- 목표 4: 기록을 주제 공통 구조(SQLite + 마크다운 노트)로 쌓는다. 에이전트가 과거 기록을 다시 질의할 수 있는 **조회 스킬**도 둔다.

### 2.2 성공 기준

- 재현율: 기준 목록(사용자 스타 12개 + 예비 스캔 라이징 31개(부록 A) + awesome-quant·awesome-ai-in-finance 링크 중 ≥1000★)에서 수집 누락이 5% 이하다.
- 중복 조사 0: 판정을 마친 뒤 재실행하면 이미 판정된 레포에 대한 LLM 호출이 0건이다(테스트로 검증).
- 판정 보정: 사용자가 직접 채점한 골드셋 20개와 비교한다. rubric-v1 확정 후 축별 점수 차이가 ±1 이내인 비율이 70% 이상이어야 한다.
- 산출물이 다 있다: 퍼널 리포트 1개, 심층분석 노트 15개 + 사용자 지정분, 아이템 원페이저 3개, 개인 툴킷 문서 1개.
- 재활용: 조회 스킬로 예시 질문 5개(§3.1-D)에 SQL 근거와 함께 답한다.
- 복원: DB 를 지우고 JSONL 로 import 하면 같은 행 수·같은 내용으로 복원된다(테스트).

### 2.3 검증 가설

사용자 반응을 재는 제품 기능은 아니다. 다만 이 조사가 **쓸모 있었는지**를 판정하는 기준이 필요해서 둔다.

| 가설 | 성공 기준 | 접을 기준 | 판정일 |
| ---- | --------- | --------- | ------ |
| 사용자가 원페이저 중 하나를 검증 트랙으로 연다 | 원페이저 3개 중 1개 이상이 "검증 진행" 판정 → 해당 제품 레포에 아이디어 문서 작성 | 0개면 브레인스토밍 입력(신호·렌즈)을 재검토하고, 2차 주제로 넘어가기 전에 방법부터 고친다 | 2026-10-24 |

## 3. 해결 방안

전체 흐름은 아래와 같다. 괄호는 LLM 사용 여부와 대략적인 건수다.

```
[수집] 검색·awesome·스타·한국 쿼리 ─→ 후보 ~4,500 (LLM 없음)
   │  gh api: search(스타 구간 분할) · README 링크 · starred
   ▼
[0단 기계 지표] 스냅샷 + stargazers/history(Δ7/30/90) + 의심 플래그 (LLM 없음)
   │  범위 컷: 유명(≥1000★) ∪ 라이징(Δ30≥300 또는 Δ30/★≥20%, ★≥100) ∪ 한국(≥50★) ∪ 사용자 스타
   ▼  → 약 700~900
[1단 선별] 설명+토픽+README 앞 2,000자 → 관련성·카테고리·한 줄 요약 (claude -p sonnet, 20개 묶음)
   │  "불확실"은 통과시킨다 (싼 판정이 확신 없으면 상위로 넘김 — Trust or Escalate)
   ▼  → 약 400~600
[2단 정밀 판정] README 앞 30,000자 + 댓글 많은 이슈 제목 30개 → 앵커 루브릭 4축 + 근거 인용 (claude -p opus, 1개씩)
   │  골드셋 20개로 먼저 보정
   ▼  선정(select): P 상위 5 ∪ I 상위 5 ∪ 라이징 상위 3 ∪ 한국 상위 2 = 15 + 사용자 지정
[3단 심층분석] 15개 + 사용자 지정 — 코드·이슈·포크·상용 파생 조사 → 노트 + 수요 신호 (대화형 스킬)
   ▼
[브레인스토밍] 신호 군집 → JTBD → 렌즈별 발산 → 군집·중복제거 → 루브릭 + 사전부검 → 사용자 선택
   ▼
원페이저 3개 · 개인 툴킷 1개 → 검증 트랙은 해당 제품 레포에서 (plan-gen)
```

### 3.1 확정 방안: 결정론적 Python 파이프라인 + `claude -p` 판정 + 대화형 스킬

기계적인 일(수집·지표·중복 판정·재개·내보내기)은 Python 이 결정론적으로 한다. 한 건씩 반복되는 판정은 `claude -p --json-schema` 를 호출해 스키마가 고정된 JSON 을 받는다. 판단 밀도가 높고 사용자와 주고받아야 하는 일(심층분석·브레인스토밍·재조회)은 Claude Code 대화형 스킬로 한다.

**"루프"는 DB 상태 기반 재개형 루프로 구현한다.**
- 레포마다 퍼널 단계가 `screening` 행으로 남는다.
- 각 명령은 "다음 단계가 아직 없는 레포"만 골라 처리한다. 중단돼도 다시 실행하면 이어서 한다.
- 근거는 두 가지다. Ralph loop 와 Anthropic 장기 실행 하네스는 상태를 컨텍스트가 아니라 파일·DB 에 두고 매 회차 새로 시작한다 [문서]. autoresearch 는 지표 과적합 사례가 있으므로 LLM 점수를 자동 최적화 목표로 쓰지 않는다 [문서].

#### B. 흐름 (명령)

| `python3 -m labbook collect stock-oss` | `config.json` 의 소스로 후보를 모은다. 검색 결과는 `gh_id`·full_name 을 이미 갖고 있다. awesome 링크와 스타 목록은 repo API 로 정규화해 최신 full_name·`gh_id` 를 얻는다(이름이 바뀐 링크는 리다이렉트로 따라가고, 404 면 엔티티를 만들지 않는다). 그 뒤 `gh_id` 기준으로 `entity` 를 upsert 한다. 이름이 바뀌었으면 key·url 을 최신으로 갱신한다. `screening(identified).sources` 에는 출처를 누적한다 | 없음 |

| `python3 -m labbook export` / `import` | export 는 테이블별로 id 를 포함한 전 컬럼을 `data/<table>.jsonl` 에 쓴다. 정렬은 snapshot 만 (taken_at, entity_id) 로 해서 주간 diff 가 파일 뒤에 붙게 하고, 나머지는 PK 순이다. import 는 빈 DB 에 마이그레이션(뷰 포함)을 먼저 적용한 뒤 행을 id 그대로 넣는다. `schema_version` 은 내보내지 않는다 | 없음 |
| 스킬 `labbook-deep-dive` | 선정 레포를 심층분석해 노트를 쓰고 `signal` 행을 넣는다 | 대화형 |
| 스킬 `labbook-brainstorm` | 신호 → JTBD → 발산 → 수렴 → 원페이저·툴킷을 만들고 `idea` 행을 넣는다 | 대화형 |
| 스킬 `labbook-query` | 스키마·뷰·대표 쿼리를 주입받아 `sqlite3` CLI 로 과거 기록에 답한다 | 대화형 |

실패와 빈 상태는 이렇게 처리한다.
- 레포가 404 면 `screening(scoped, exclude, 'gone')` 으로 기록한다.
- 검색 레이트리밋(30/min)에 걸리면 `Retry-After`·리셋 시각까지 기다렸다가 재시도한다.
- `claude -p` 는 타임아웃 600s 로 호출한다. 타임아웃·스키마 검증 실패·인용 검사 실패(§C)가 나면 1회 재시도한다. 또 실패하면 `screening(..., 'error')` 로 남긴다. `error` 는 다음 실행의 대기열에 다시 들어간다(한 번만 쓰는 규칙의 유일한 예외).
- 판정할 대상이 없으면 "대기 0건"을 출력하고 종료한다.

#### C. 판정 설계 (문헌 근거)

- **절대점수 + 앵커 루브릭**을 쓴다. 쌍대비교는 겉보기 요소에 뒤집히는 비율이 더 높고(35% vs 9%) [문서: 2504.14716], Claude 쌍대 랭커의 아이디어 판정 정확도는 53% 였다 [문서: Si 2024]. 루브릭과 앵커를 주면 인간 판정과 상관 0.9 수준이 나온다 [문서: Prometheus].
- **근거를 먼저 쓰고 점수는 그다음**에 매긴다. 축마다 README·이슈에서 인용문을 요구한다. 스키마(`minLength`)만으로는 지어낸 인용이 통과하므로, 코드가 따로 검사한다. 공백을 정규화한 뒤 인용이 입력 텍스트의 부분문자열인지 확인하고, 아니면 재시도 대상으로 둔다.
- **4축을 따로 둔다.** 목적이 두 개(개인 투자·인디)라서 합산 점수는 만들지 않는다. 심층분석 선정은 축별 상위를 합친 집합으로 한다.

| 축 | 1 (앵커) | 3 | 5 |
|----|---------|---|---|
| P 개인 활용도 | 내 투자(미국·한국 주식, 중장기)와 무관하거나 실행에 유료 데이터·인프라가 필수 | 조건부로 쓸 만함(설정 반나절, 무료 데이터 일부) | 오늘 무료 데이터로 돌려 리서치에 쓸 수 있음 |
| I 인디 기회 | 개발자 전용이고 수요 신호가 없음 | 비개발자 수요 신호는 있으나 대체재가 많음 | 비개발자의 명시적 요청(호스팅·현지화·쉬운 설치)이 반복되고 한국어 공백이 있음 |
| N 차용 가치 | 흔한 구조의 재구현 | 부분적으로 새로운 기법 | 가져다 쓸 설계·아이디어가 분명함 |
| T 주장 신뢰도 | 성과 주장만 있고 방법 불명 | 백테스트 방법은 공개했으나 look-ahead 대책이 없음 | 컷오프 이후·라이브·넓은 종목군 평가가 있거나 성과를 주장하지 않는 도구 |

- **보정**: 전수 판정 전에 사용자가 골드셋 20개(사용자 스타 12 + 카테고리별 대표 8)를 직접 채점한다. `judge --gold` 로 차이를 보고 루브릭을 고친 뒤 v1 으로 확정한다. Anthropic 리서치 시스템도 평가를 약 20개로 시작했다 [문서].
- **라이징·의심 판정**: StarScout 식 계정 판별은 stargazer 목록이 막혀서 불가능하다 [실측]. 대신 아래 플래그를 쓴다. 플래그가 선 레포는 제외하지 않고 퍼널에 "의심"으로 표시해 사람이 본다.
  - 일별 급등: 3일 안에 30일 증가분의 70% 이상이 몰림
  - watchers/★ < 1.5%
  - 레포 나이 대비 커밋 수가 과소함
  - README 에 exe·zip 설치 링크가 있음

#### D. 조사 기록 체계 (주제 공통 — 사용자 추가 요청)

Karpathy "LLM Wiki"(2026-04)의 원자료 / 컴파일된 노트 / 스키마 3층, PRISMA 스크리닝 로그, 지표 스냅샷(git scraping)을 1인 규모로 줄여 조합한다 [문서]. 그래프 DB·벡터 검색·MCP 서버는 수천 건 규모에서 과하므로 뺀다(§7.3).

```
labbook/                    Python 패키지 (표준 라이브러리만)
  migrations/001_init.sql
topics/stock-oss/
  config.json               수집 쿼리·awesome 목록·범위 임계치
  rubric-v1.md              판정 루브릭 (버전을 파일명에 둔다)
  gold.jsonl                사용자 골드 점수 — 한 줄 {"repo":"owner/repo","P":4,"I":3,"N":3,"T":2,"note":"한 줄 이유"}
  recall-baseline.txt       재현율 점검 기준 목록 (owner/repo 한 줄씩, 부록 A)
  notes/  ideas/  reports/  심층·아이디어·퍼널 (마크다운, frontmatter 로 엔티티 연결)
  toolkit.md
  index.md                  노트·아이디어 한 줄 카탈로그 (에이전트가 먼저 읽는다)
  log.md                    "## [날짜] 동작 | 내용" append-only
data/*.jsonl                테이블별 정렬 JSONL — git 의 이력 정본
.cache/                     API 원응답·README·llm/ 호출 cwd·repos/ 얕은 clone (gitignore, 다시 받을 수 있음)
labbook.db                  작업 DB (gitignore, `import` 로 재구성)
```

- **SQLite 는 작업 DB 로 쓰고 git 에는 JSONL 을 커밋한다.** 바이너리 DB 를 커밋하면 diff·리뷰가 안 되고 레포가 비대해진다 [문서: Willison 2023]. 1인·순차 작업이라 JSONL 동기화 충돌 문제(beads 가 Dolt 로 옮긴 이유)는 해당하지 않는다.
- **원자료와 판단을 분리한다.** 원응답은 캐시로 두고, 판정에는 `rubric_version`·`model`·`input_sha`(README blob sha)·인용을 함께 남긴다.
- **엔티티는 주제 공통이다.** upsert 기준은 `gh_id` 다. `github:owner/repo` 키는 최신 이름을 따라 갱신되는 표시용 키다. 노트 frontmatter 에는 `gh_id` 를 병기해 이름 변경 뒤에도 연결이 유지된다. 다음 주제(예: 서비스 벤치마크)에서 같은 레포·회사가 나오면 같은 엔티티에 연결된다.

```sql
-- labbook/migrations/001_init.sql (요지)
CREATE TABLE entity (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,              -- 'github_repo' (다음 주제에서 'service' 등 추가)
  key TEXT NOT NULL UNIQUE,        -- 'github:virattt/ai-hedge-fund' (소문자)
  gh_id INTEGER UNIQUE,
  url TEXT, first_seen_at TEXT NOT NULL
);
CREATE TABLE screening (           -- PRISMA 흐름: 단계별 판정과 사유
  topic TEXT NOT NULL, entity_id INTEGER NOT NULL REFERENCES entity(id),
  stage TEXT NOT NULL,             -- identified | scoped | triaged | judged | deep
                                   -- scoped 는 refresh 마다 upsert, 나머지는 한 번만 씀 (error 만 재시도)
  decision TEXT NOT NULL,          -- include | exclude | unsure | error
  reason TEXT, sources TEXT,       -- sources: identified 단계의 출처 JSON 배열
  decided_at TEXT NOT NULL,
  PRIMARY KEY (topic, entity_id, stage)
);
CREATE TABLE snapshot (            -- 지표 이력 (레포당 하루 1행)
  entity_id INTEGER NOT NULL REFERENCES entity(id),
  taken_at TEXT NOT NULL,          -- UTC 'YYYY-MM-DD'
  stars INTEGER, forks INTEGER, watchers INTEGER, open_issues INTEGER,
  pushed_at TEXT, archived INTEGER, d7 INTEGER, d30 INTEGER, d90 INTEGER,
  flags TEXT,                      -- 의심 플래그 JSON 배열
  PRIMARY KEY (entity_id, taken_at)
);
CREATE TABLE judgment (
  id INTEGER PRIMARY KEY, topic TEXT NOT NULL, entity_id INTEGER NOT NULL REFERENCES entity(id),
  stage TEXT NOT NULL,             -- triage | full
  rubric_version TEXT NOT NULL, model TEXT NOT NULL,
  input_sha TEXT,                  -- 판정에 쓴 README 의 blob sha
  category TEXT, summary_ko TEXT,
  scores TEXT,                     -- {"P":4,"I":3,"N":3,"T":2}
  evidence TEXT,                   -- {"P":"인용…",…}
  judged_at TEXT NOT NULL,
  UNIQUE (topic, entity_id, stage) -- 재판정 없음: 한 단계 한 번
);
CREATE TABLE signal (              -- 수요 신호: 주제를 넘어 GROUP BY 로 재활용
  id INTEGER PRIMARY KEY, topic TEXT NOT NULL, entity_id INTEGER REFERENCES entity(id),
  kind TEXT NOT NULL,              -- demand | pain | gap
  quote TEXT NOT NULL, source_url TEXT NOT NULL, weight INTEGER, found_at TEXT NOT NULL,
  UNIQUE (topic, source_url, quote) -- 심층분석을 다시 돌려도 INSERT OR IGNORE 로 중복 없음
);
CREATE TABLE idea (
  id INTEGER PRIMARY KEY, topic TEXT NOT NULL, title TEXT NOT NULL,
  jtbd TEXT, lens TEXT, signal_ids TEXT, scores TEXT,
  status TEXT NOT NULL,            -- draft | shortlist | validating | dropped
  reason TEXT, doc_path TEXT, created_at TEXT NOT NULL
);
CREATE VIEW v_repo_latest AS …     -- 엔티티 + 최신 스냅샷 + full 판정
```

- **중복 조사 방지**는 스키마로 보장한다. `judgment` 에 `UNIQUE(topic, entity_id, stage)` 를 두고, 명령은 해당 단계 행이 없는 레포만 고른다. 새로 발견된 레포와 새로 범위에 들어온 레포(예: 라이징 진입)만 LLM 으로 간다. 루브릭이 바뀌어도 자동으로 재판정하지 않는다(§7.3).
- **재조회 스킬 `labbook-query`** 는 MCP 없이 스키마·뷰·대표 쿼리를 스킬 본문에 두고 `sqlite3` CLI 로 답한다. 공식 SQLite MCP 서버는 2025-05 에 아카이브됐다 [문서]. 예시 질문 5개(성공 기준):
  1. 심층분석에서 한국 시장 지원 요청 `signal` 이 나온 레포는?
  2. 지난 refresh 대비 Δ30 이 두 배가 된 레포는?
  3. P≥4 이고 T≥4 인 레포는?
  4. `demand` 신호가 가장 많이 모인 JTBD 는?
  5. 1단에서 "금융 무관"으로 뺀 레포 중 ★ 상위 10개는? (제외 판정 점검용)
- 좋은 답변은 노트에 다시 적고 `index.md` 를 갱신한다(Karpathy 의 write-back). 이것은 스킬 출력 형식으로 정한다.

#### E. 브레인스토밍 설계 (`labbook-brainstorm` 스킬)

1. **입력을 고정한다.** 입력은 `signal` 행, 심층 노트, GuruNote 경쟁·규제 조사, 사용자 자산·제약(1인, 한국 투자자 대상, GuruNote 워커·봇, 월정액 LLM)이다. 레포 목록만으로는 발산하지 않는다.
2. **문제에서 출발한다.** 신호를 군집해 JTBD 문장("상황-동기-결과")으로 만들고, 각 문장에 근거 신호 수를 붙인다 [문서: Christensen 2016].
3. **렌즈를 강제해 발산한다.** 쏠림을 줄이려고 JTBD × 렌즈마다 생성한다 [문서: STORM 관점 통제, Meincke 2024]. 사용자가 낸 아이디어도 같은 풀에 넣는다.
   - 호스팅·관리형 (오픈소스 → SaaS, Plausible 모델)
   - 한국화 (KRX·DART·KIS, 한국어)
   - 언번들 (한 기능만 떼기)
   - 곡괭이 (데이터·MCP·에이전트 스킬 공급)
   - 신뢰·검증 (AI 신호의 포워드 성적표 — 문제 3 의 역이용)
   - 콘텐츠·교육
   - GuruNote 자산 결합
4. **군집·중복제거**: 비슷한 아이디어를 묶고 군집마다 대표 하나를 남긴다 [문서: co-scientist Proximity].
5. **수렴**: 앵커 루브릭으로 절대점수를 매긴다(수요 근거, 기존 대안 대비 차별성, 1인 실현성, 규제 위치, 수익화, 자산 재사용). 상위권에는 **사전부검**("6개월 뒤 실패한 이유")을 붙인다. **최종 3개는 사용자가 고른다.** LLM 점수는 순서를 정하는 보조로만 쓴다. 아이디어 평가는 인간끼리도 56% 만 일치한다 [문서: Si 2024].
6. **규제 위치 라벨은 필수다** [문서: 자본시장법 101조, 2024-08 개정, FSC 2021 유권해석].
   - 무료 정보·도구
   - 유료 비개인화 추천 → 유사투자자문 신고
   - 개인 맞춤 추천·자동매매 연동 → 등록업, 인디로는 불가
7. **출력**: 원페이저(§3.1-A ④)에 검증 가설을 적는다. 검증은 LabBook 이 아니라 해당 제품 레포(GuruNote 또는 신규)의 아이디어 문서·plan-gen 으로 넘긴다.

```python
# labbook/metrics.py — 라이징·의심 플래그 (요지)
def momentum(history):            # stargazers/history page 1 (최신 주 먼저, 일별 days)
    days = [d for w in history for d in reversed(w["days"])]   # 최신일부터
    return sum(days[:7]), sum(days[:30]), sum(days[:90])

def spike_flag(days30):
    top3 = max(sum(days30[i:i+3]) for i in range(len(days30) - 2))
    return sum(days30) > 0 and top3 / sum(days30) >= 0.7
```

`history` 의 `days` 순서(요일순 여부)와 page 1 이 90일을 덮는지는 구현 1단계 테스트 픽스처로 확정한다. 한 페이지는 30주다 [실측].

#### 장점

- 결정론적 부분이 테스트된다. 재개·중복 방지가 스키마와 SQL 로 보장된다.
- 판정은 월정액 구독 안에서 돈다. 개인 연구라 GuruNote 에서 쟁점이 된 "제품용 구독 사용" 문제가 없다.
- 기록 체계가 주제 공통이라, 다음 주제에서 `collect` 소스와 루브릭만 바꾸면 된다.

#### 단점

- `claude -p` 호출 약 550회(1단 약 40회 묶음 + 2단 약 500회 개별)가 구독 한도를 나눠 쓴다. 며칠에 나눠 돌려야 할 수 있다 [추정].
- 판정 모델이 하나(Claude)라서 다중 계열 배심원(PoLL)의 편향 감소 효과는 없다. 골드셋 보정으로 대신한다.

## 5. 권장 사항

### 5.1 확정 방안 (2026-09-26 사용자 결정)

- 구조: 수집·지표·퍼널·내보내기는 Python(표준 라이브러리)으로 한다. 1·2단 판정은 `claude -p --json-schema` 로 하고, 1단은 sonnet, 2단은 opus 를 쓴다. 심층분석·브레인스토밍·재조회는 대화형 스킬로 한다.
- 기록: SQLite 는 작업 DB 로 쓰고(gitignore), git 에는 테이블별 JSONL 을 커밋하며, 서술은 마크다운 노트로 남긴다.
- 범위: 유명 ≥1000★ ∪ 라이징 ∪ 한국 ≥50★ ∪ 사용자 스타.
- 보정: 골드셋 20개로 한다.
- 심층분석 대상: 축별 고정 할당 15개에 사용자 지정분을 더한다.

### 5.2 근거

- 사용자의 핵심 요구 "한 번 조사한 것은 다시 조사하지 않는다"를 테스트 가능한 형태로 보장하려면 결정론적 코드가 대기열을 쥐어야 한다.
  - 기각한 대안 1: Claude Code 네이티브(스킬·에이전트가 전부 수행). 800건 규모에서 재개·중복 방지를 테스트할 수 없다.
- 수백 건 반복 판정은 스키마를 고정한 단건 호출이 적합하고, 사용자와 주고받는 판단은 대화형이 적합하다. 두 성격이 섞인 작업이라 하이브리드가 맞다.
- 다중 계열 저가 API 판정(OpenRouter)은 편향 감소 효과가 불확실한데 [문서: Hivemind], 종량 과금·API 키 부담은 확실하다.
  - 기각한 대안 2: 이 방식은 골드셋 보정이 실패하면 다시 검토한다. `run_claude` 를 한 함수로 두어 옮기는 비용을 낮춘다.
- SQLite 파일을 그대로 커밋하면 diff·리뷰가 안 되고 레포가 비대해진다.
- 원점 검토로 방향을 세 가지 틀었다.
  - 스타 수 대신 추세·의심·수요 신호를 본다.
  - 매매시점 제시를 전제가 아니라 신뢰 축(T)으로 평가한다.
  - 레포 목록이 아니라 수요 신호에서 브레인스토밍한다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- `stargazers/history` 는 3주 된 신규 엔드포인트다. 형식 변경이나 제한 강화 가능성이 있다. / 대응: 어댑터에 격리한다. 실패하면 주간 `snapshot` 의 스타 수 차분으로 대신한다(첫 주는 Δ 없이 범위 컷에서 ★ 기준만 적용).
- 구독 한도 소진. / 대응: `--limit N` 으로 나눠 돌린다(재개형). 1단은 20개씩 묶어 호출 수를 줄이고, 2단 입력은 README 30,000자로 자른다.
- `refresh` 의 history 호출이 후보 전체(약 4,500개)라 core 한도(5000/h)를 약 1시간 쓴다. / 대응: 주 1회 실행을 전제로 한다. 레이트리밋에 걸리면 리셋까지 기다린다(3단계 거동). 같은 날 이미 스냅샷이 있는 레포는 건너뛰어, 중단 후 재실행해도 이어서 진행된다.
