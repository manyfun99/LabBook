### 1.2 문제점

- **문제 1 — 재료가 독자용 형식이 아니다.** 노트는 이슈 번호와 코드 경로가 빽빽한 조사 기록이다. 1편의 독자는 AI 매매 도구를 깔까 말까 고민하는 개인 투자자다. 1편의 구성·길이·말투가 아직 정해지지 않았다.
- **문제 2 — 측정 방법이 정해지지 않았다.** 원페이저의 성공 기준은 "조회 1,000 · 도구명을 지목한 질문 10건 · 설치 대상을 바꿨다는 말 3명"이다. 그런데 조회를 어디서 세는지, 무엇을 "지목 질문"으로 볼지, 어디에 기록할지가 없다. GeekNews 는 링크 게시가 기본이라 본문 조회가 링크 대상에서 잡힌다.
- **문제 3 — 일정이 빠듯하다.** 오늘이 2026-10-06 이고 판정일은 10-24 다. 성공 기준이 "게시 2주 안"이므로 **10-10 까지는 게시해야** 측정 기간이 2주가 된다.
- **문제 4 — 수치가 낡았을 수 있다.** 노트는 9-27~28 기준이다. 그 뒤로 README 성과 문구나 대시보드 수치가 바뀌었을 수 있다. 공개 글에 틀린 수치가 실리면 원페이저 사전부검 3번(원저자와 충돌)으로 바로 이어진다.
- **문제 5 — 법·평판의 경계선.** 도구 평가가 종목·매매 판단으로 읽히면 안 된다(원페이저 규제 위치, 자본시장법 §7③). 특정 프로젝트의 주장을 깎는 서술에는 근거 링크가 있어야 한다.

#### 흐름과 상태

```
10-07 초안·신선도 확인·근거 대조 → 10-08 사용자 검토 ──┬─ 수정 요청 → 고쳐서 다시 검토
```

- 승인 없이는 게시 단계로 넘어가지 않는다. Claude 는 어떤 채널에도 게시하지 않는다. 승인을 받은 뒤 본문(정본·클리앙판)이 한 글자라도 바뀌면 다시 승인을 받는다.

### 3.2 측정 — 조회·지목 질문의 정의

| 지표 | 정의 | 출처 |
|---|---|---|
| 조회 | 클리앙 게시글 조회수 + GitHub 경로 `…/blob/main/topics/stock-oss/posts/duediligence-01.md` 의 `count` | 클리앙 공개 페이지(WebFetch) · `gh api …/traffic/popular/paths` |
| 지목 질문 | 댓글·답글·DM 중 **특정 도구(레포) 이름을 들어** 쓸지·비교·설치·신뢰를 묻는 것. 같은 사람의 연속 질문은 1건이고, 작성자 본인 글은 빼고 센다 | 클리앙·GeekNews 공개 페이지(WebFetch) · DM 은 사용자가 건수만 알려 준다 |
| 설치 대상 변경 | "이 표를 보고 X 대신 Y 를 보기로 했다"처럼 **명시적으로 말한 사람** 수 | 위와 같음 |

- 집계는 두 번 한다. 중간 집계는 게시 7일 뒤, 최종 집계는 **10-23** 이다. 단, GitHub 경로 조회수는 **게시일 +13일과 10-23 중 이른 날**에 읽는다. `popular/paths` 는 최근 14일 합계만 주므로, 늦게 읽으면 조회가 가장 많은 게시 첫날이 창에서 빠진다. 반대로 집계가 이틀가량 늦게 들어오므로(2026-10-06 조회 시 마지막 버킷이 10-04) 마지막 1~2일 조회는 빠질 수 있다. 읽을 때 `traffic/views` 의 마지막 `timestamp` 를 함께 적어 반영된 날짜를 남긴다. 게시 전후로 작성자가 그 경로를 여는 것도 조회에 잡히므로 `uniques` 를 함께 적는다.
- 집계·판정 줄은 **KST 09:00 이후**에 쓴다. 로그 날짜는 UTC 라서 그 전에 쓰면 전날 날짜가 찍힌다(인계 §2, 2026-09-28 사실).
- 댓글 읽기는 공개 페이지 조회만 한다. 댓글을 달거나 답하는 일은 사용자가 한다. WebFetch 가 막히거나 로그인이 필요하면, 조회수와 지목 질문 수를 사용자에게 한 줄로 묻는다.
- 기록에는 **건수만** 남긴다. 댓글 작성자 닉네임, 댓글·DM 원문은 `log.md`·레포·DB 어디에도 저장하지 않는다.

### 3.3 기록

코드 변경이 없으므로 "현재 코드/개선 코드" 대신 기록 형식을 정한다.

`topics/stock-oss/log.md` (UTC 날짜, 기존 `## [날짜] 종류 | 내용` 형식):

```
## [2026-10-09] publish | duediligence-01 · 클리앙 <URL>
## [2026-10-09] publish | duediligence-01 · GeekNews <URL>
## [2026-10-09] idea-load | 추가 0 · 갱신 1 · 전체 70        ← idea-load 가 스스로 남기는 줄 (cli._log)
## [2026-10-16] reaction | duediligence-01 D+7 · 조회 N(클리앙 a + GitHub b, uniques c, 반영 ~MM-DD) · 지목 질문 m · 설치 변경 k
## [2026-10-23] reaction | duediligence-01 최종(D+n) · …
## [2026-10-24] verdict | oss-duediligence-report · 성공|보류|접음 · 근거 한 줄 (측정 기간 n일)
```

`idea` 상태 — `.cache/brainstorm/status-duediligence.jsonl` 에 한 줄을 쓰고 `python3 -m labbook idea-load stock-oss <파일>` → `export`:

```json
{"title": "AI 주식 오픈소스 실사 보고서 + 성과 주장 감사", "status": "validating"}
```

판정 결과가 접기면 `{"title": …, "status": "dropped", "reason": "2026-10-24 판정: 조회 N·지목 m — 감사 5항목을 install-survival-guide-kr 로 합침"}` 을 넣는다. 성공·보류면 `validating` 을 그대로 둔다. 제목은 갱신 키이므로 바꾸지 않는다(인계 §4).

원페이저 `oss-duediligence-report.md` 맨 끝에 `- **검증 결과 (2026-10-24)**: …` 한 줄을 더한다. 인계 문서 §3.0 은 판정 결과로 갱신한다.

## 5. 권장 사항

### 5.1 확정 방안 (2026-10-06 사용자 결정)

- 채점표 5개: **★ 상위 4개(tradingagents · mirofish · ai-hedge-fund · vibe-trading) + 한국 1개(prism-insight)**

- GitHub 공개 파일을 정본으로 두면 GeekNews 조회를 traffic API 로 잴 수 있다. 방법·원자료가 공개돼 있다는 점은 원저자 반론에도 대응이 된다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- 사실 오류·원저자 반발: 공개 글이라 되돌리기 어렵다 / 대응: 단계 2 신선도 확인과 단계 4 전건 대조를 거친다. 깎는 서술에는 링크를 붙이고 장점도 쓴다. 제보가 오면 §3.1 의 정정 절차를 따른다.
- 투자 조언으로 읽힘: 대응 — 종목·매매 시점을 쓰지 않는다. 평가 기준(5항목)을 먼저 공개한다. 면책 한 줄을 둔다.
- 게시판 규정 위반(홍보성 글): 대응 — 비상업 글이고 링크는 방법 공개용 1개다. 게시판 선택과 규정 확인은 게시하는 사용자가 판단한다.
- 측정 왜곡: GitHub traffic 에 작성자 본인 열람이 섞인다. 14일 창이 지나면 사라지고, 집계는 이틀가량 늦게 들어온다 / 대응: `uniques` 와 반영 날짜를 함께 적는다. 게시 7일 뒤와, 게시일 +13일·10-23 중 이른 날에 읽는다. 게시 전에는 main URL 을 여는 일을 줄인다.
- 측정 기간 부족(게시 지연): 대응 — 판정일은 유지하고 기간을 `verdict` 줄에 적는다.
- 판정 주체의 한계: 노트·판정이 모두 Claude 판단이다(인계 §2 골드셋 채점자) / 대응: 본문 "방법과 한계"에 밝힌다. 사람이 검증했다고 쓰지 않는다.
- 개인정보: 이슈 인용에 작성자 계정이 따라올 수 있다 / 대응: 계정명을 쓰지 않는다. 인용문은 신호 적재 때 개인정보 형태를 이미 걸렀다(3차 §3.4).
- 개인정보(집계, 위험 경로): 클리앙·GeekNews 댓글과 사용자에게 온 DM 은 제3자의 글이다 / 대응: 건수만 기록한다. 닉네임과 원문은 `log.md`·레포·DB 에 저장하지 않는다. DM 은 내용을 받지 않고 건수만 받는다(§3.2).

### 7.2 의존성

- 사용자: 본문 승인, PR 머지, 클리앙·GeekNews 계정으로 게시, DM 건수 공유.
- `gh` 인증(traffic API 는 레포 push 권한이 필요하다 — 2026-10-06 확인).
- 하네스 마찰: plan-execute·plan-verify 는 코드·테스트 작업을 전제한다. 이 계획은 콘텐츠 작업에 수동 단계(8·9·10)와 기간을 둔 측정(12~14)이 섞여 있다. 그래서 TDD 행이 해당하지 않고, 실행은 단계 11 에서 판정일까지 멈춰 있게 된다. indie-forge 에 "콘텐츠·검증 트랙 계획" 유형으로 모아 둔다.

### 7.3 범위 밖 / 향후 작업

- 2편 이후·429개 전체 카탈로그 공개·자동 갱신·영어판·유료화 — 판정 결과를 보고 정한다(원페이저 범위 밖).
