### 1.2 문제점

- **문제 1 — 신호가 레포에 쏠려 있다.** tradingagents 38 · ai-hedge-fund 35 로 상위 2개가 371건의 20% 다. 신호를 레포 단위로 묶으면 JTBD 가 큰 레포의 이슈 트래커를 그대로 따라가고, 레포 1곳에서만 나온 요구가 "수요"로 승격된다.
- **문제 2 — 한 맥락에서 발산하면 쏠린다.** 원 계획 문제 4 의 근거대로 LLM 아이디어는 흔한 쪽으로 수렴한다. 렌즈 7개를 한 세션이 순서대로 돌면 앞 렌즈의 아이디어에 앵커링된다.
- **문제 3 — `idea` 적재 스니펫이 깨져 있다.** 스킬 출력 3번이 `sqlite3 labbook.db "INSERT … datetime('now')"` 형태다. ① `found_at`/`created_at` 형식이 다른 테이블(`2026-09-27T01:37:47+00:00`)과 어긋나고, ② JTBD·사유 문자열에 작은따옴표가 들어가면 SQL 이 깨지며, ③ 문서 속 heredoc 이라 회귀 테스트가 잡지 못한다. `signal` 쪽은 3차 §3.3 에서 파라미터 바인딩으로 고쳤지만 `idea` 는 그대로 남았다.
- **문제 4 — 적재를 두 번 한다.** 발산 결과는 `draft` 로, 사용자가 고른 뒤에는 `shortlist`/`dropped` 로 같은 아이디어를 다시 쓴다. `idea` 테이블에 UNIQUE 가 없어서 그냥 INSERT 하면 중복 행이 생긴다.
- **문제 5 — 원페이저 3개를 고르는 방식이 정해져 있지 않다.** 스킬은 "사용자가 고른다"까지만 적혀 있다. 3차 `select` 확인(후보표 한 장 + 버튼 문항)이 선례다.
- **문제 6 — 툴킷 대상 범위가 없다.** 19개 전부인지 P 상위인지, 쓰지 않기로 한 것을 남기는지가 정해져 있지 않다.

### 3.1 JTBD 군집 — 레포가 아니라 인용 내용으로 묶는다

메인 세션이 SQL 한 번으로 신호 전량을 작업 파일에 내린다. 레포 이름은 **근거 계산용**으로만 쓰고 군집 키로 쓰지 않는다.

```sh
sqlite3 -noheader -separator $'\t' labbook.db "
SELECT s.id, s.kind, s.weight, replace(e.key,'github:',''), replace(replace(s.quote, char(10), ' '), char(9), ' ')
FROM signal s JOIN entity e ON e.id = s.entity_id
WHERE s.topic = 'stock-oss' ORDER BY s.kind, s.weight DESC;" > .cache/brainstorm/signals.tsv
```

군집 규칙:

1. 인용이 말하는 **요구·불편의 내용**으로 묶는다. 같은 레포의 신호가 여러 군집에 흩어져도 된다.
2. 군집마다 JTBD 문장을 쓴다 — "\<상황\>에서 \<동기\>하려는 \<누구\>가 \<결과\>를 원한다".
3. 문장마다 `signal_ids`, **근거 레포 수**, weight 합을 붙인다.
4. **근거 레포가 1곳뿐인 군집은 `단일` 로 표시한다.** 버리지는 않지만(예: 한국 데이터 공백은 financedatareader 한 곳에 몰려 있다) 6기준의 "수요 근거" 점수 상한이 3 이다.
5. 한 레포가 군집 근거의 50% 를 넘으면 ⚠ 를 붙이고 역시 "수요 근거" 상한을 3 으로 둔다. tradingagents·ai-hedge-fund 가 군집을 끌고 가는 것을 막는 장치다.

출력 샘플 (`.cache/brainstorm/jtbd.md`):

```
| # | JTBD | 근거 signal | 레포 | weight | 표시 |
|---|------|------------|------|--------|------|
| 1 | 무료 시세 API 가 막히는 상황에서 리서치를 계속하려는 개인 퀀트가 끊기지 않는 데이터 공급을 원한다 | 12,47,88,131,204,… (17) | 5 | 143 | |
| 2 | LLM 분석 결과를 믿을지 판단하려는 개인 투자자가 그 신호의 사후 성적표를 원한다 | 33,61,150,…  (9) | 4 | 61 | |
| 3 | KRX 로그인 필수화 뒤 한국 데이터를 쓰려는 개인이 끊기지 않는 국내 소스를 원한다 | 201,205,…  (11) | 2 | 58 | ⚠ fdr 8/11 |
```

### 3.2 발산 — 렌즈별 서브에이전트 병렬 (배치 4 + 3)

3차 심층분석의 분할 방식을 그대로 쓴다. **서브에이전트는 파일만 쓰고, DB·문서는 메인이 쓴다.**

- 배치 1: 호스팅·관리형 / 한국화 / 언번들 / 곡괭이
- 배치 2: 신뢰·검증 / 콘텐츠·교육 / GuruNote 자산 결합

각 서브에이전트에 같은 입력을 준다. 서로의 출력은 보지 못한다.

| 입력 | 경로 |
|---|---|
| JTBD 표 | `.cache/brainstorm/jtbd.md` |
| 신호 전량 | `.cache/brainstorm/signals.tsv` |
| 노트 카탈로그 | `topics/stock-oss/index.md` (필요하면 `notes/*.md` 개별 열람) |
| GuruNote 발췌 | `.cache/brainstorm/gurunote-brief.md` — **메인이 미리 만든다** |
| 자산·제약·규제 라벨 | 위 브리프에 포함 |

GuruNote 문서는 다른 레포(`~/Workspace/Indy/GuruNote`)에 있어 서브에이전트가 직접 읽게 하면 경로 권한과 컨텍스트가 늘어난다. 메인이 경쟁 지형(§1.1·1.3·1.5)·규제(§4)·관심기업 아이디어의 검증 방식(§4)을 한 파일로 추려 둔다.

서브에이전트 출력은 `.cache/brainstorm/ideas-<렌즈>.jsonl` 한 줄 한 아이디어다.

```json
{"title": "…", "lens": "한국화", "jtbd_ids": [1, 3], "signal_ids": [201, 205, 219],
 "pitch": "한 줄 설명", "alt": "기존 대안(추정)", "regulation": "무료 정보·도구",
 "feasibility": "1인 실현성 근거 한 줄", "reuse": "재사용 자산"}
```

- 렌즈당 5~8개. 규제 라벨은 필수이고 스킬의 3분류만 쓴다.
- `signal_ids` 는 `signals.tsv` 에 실재하는 id 여야 한다. 신호 근거 없이 사용자 자산·제약에서만 나온 아이디어는 빈 배열로 두고, 수렴에서 "수요 근거" 1점이 고정된다.
- 배치 예산: 3차 심층분석은 레포당 4~10분(웹·clone 포함)이었다. 이번 발산은 로컬 파일만 읽으므로 렌즈당 3~6분, 배치당 6~10분으로 본다. 한 배치가 15분을 넘으면 남은 렌즈를 다음 배치로 미룬다.
- **서브에이전트는 웹을 쓰지 않는다.** 기존 대안은 조사 기록·GuruNote 발췌 범위에서 "추정"으로 적고, 실제 경쟁 확인은 메인이 상위 후보에만 한다(§3.3). 렌즈 7개가 각자 웹 검색을 하면 시간이 크게 늘고, 차별성 판단이 필요한 시점은 수렴 단계다.

### 3.3 수렴 — 6기준 절대점수 + 사전부검

메인이 7개 파일을 합쳐(raw 35~56) 비슷한 것을 묶고 군집마다 대표 하나를 남긴다(목표 12~18). 묶인 아이디어의 `signal_ids`·`lens` 는 대표에 합친다.

합쳐진 쪽도 버리지 않는다 — `dropped` + `중복: <대표 제목>` 으로 함께 적재해 발산 이력을 남긴다(§3.4). `.cache/` 는 gitignore 라 적재하지 않으면 사라진다.

대표마다 6기준에 1~5 절대점수를 매긴다. 둘씩 붙여 비교하지 않는다. 앵커는 아래로 고정한다 — 스킬에는 기준 이름만 있고 앵커가 없어서 회차마다 기준이 흔들린다.

| 기준 | 1 | 3 | 5 |
|---|---|---|---|
| 수요 근거 | 단일 레포 신호 1~2건, 또는 신호 근거 없음(빈 `signal_ids` — **1 고정**) | 레포 2곳 이상·신호 5건 이상 | 레포 4곳 이상·신호 12건 이상·weight 합 50 이상 |
| 차별성 | 증권사 앱·네이버 금융이 이미 무료로 준다 | 대안은 있으나 한국어·한국 데이터·자동화에서 빈다 | 조사 기록·GuruNote 문서에서 같은 것을 하는 곳을 찾지 못했다 |
| 1인 실현성 | 상시 운영 인프라나 데이터 계약이 필요하다 | 4주 안 MVP, 주 1회 운영 | 기존 자산에 얹어 2주 안 |
| 규제 위치 | 등록업(인디 불가) | 유사투자자문 신고 필요 | 무료 정보·도구 |
| 수익화 | 과금 경로가 없다 | 유료 전환 경로는 보이나 근거는 유추다 | 같은 영역의 실제 과금 사례를 조사에서 확인했다(edgar.tools 월 $25~80, go-stock VIP 월 28.8 RMB, worldmonitor 유료 패널) |
| 자산 재사용 | 새로 다 만든다 | 패턴만 재사용한다 | GuruNote 워커·텔레그램 봇·`claude -p` 파이프라인을 그대로 쓴다 |

- 차별성 5점은 "찾아봤는데 없다"일 때만 준다. 검색이 실패했거나 확인하지 못했으면 **4 를 상한**으로 두고 그 사실을 적는다 — "안 찾아봤다"와 "없다"를 구분한다.
- **규제 1점(등록업)은 후보표에서 뺀다.** 뺀 것도 `idea` 에 `dropped` + 사유로 남긴다.
- 상위 6개에만 ① 실제 경쟁 확인(웹·GuruNote 문서), ② 사전부검 3줄("6개월 뒤 실패했다면 그 이유")을 붙인다.
- 점수는 순서를 정하는 보조다. 합산 순위를 최종 결정으로 쓰지 않는다(원 계획 §3.1-E 5).

**사용자 선택** — 3차 `select` 확인 방식을 따른다. 후보표(상위 8개: 제목·JTBD·규제·6점수·사전부검 요약)를 한 장으로 보여 주고 버튼 2문항으로 묻는다. 후보가 8개보다 적으면 문항 수를 줄인다.

| 문항 | 형태 |
|---|---|
| 1 | "상위 4개 중 원페이저로 만들 것" — 다중 선택 |
| 2 | "차순위 4개 중 추가할 것 (없으면 없음)" — 다중 선택 |

원페이저 파일명은 영문 kebab-case 2~4단어다(`topics/` 디렉터리·`config.json` 과 같은 결). `idea.doc_path` 는 **레포 루트 기준** `topics/stock-oss/ideas/<slug>.md` 로 적고, `index.md` 링크는 노트와 같이 주제 디렉터리 기준 `ideas/<slug>.md` 로 적는다.

합이 3개가 되게 고른다. 후보표에 없는 것을 원하면 "Other" 로 직접 적는다. 0개면 §2.3 의 접을 기준이 발동한다 — 원페이저를 억지로 쓰지 않고 멈춰서 입력·렌즈를 재검토한다.

### 3.4 `labbook idea-load` 명령 승격

문제 3·4 를 없앤다. 스킬 출력 3의 `sqlite3` 스니펫을 명령 호출로 바꾼다.

```
python3 -m labbook idea-load <주제> <파일.jsonl>
```

입력 한 줄:

```json
{"title": "…", "jtbd": "…", "lens": "한국화", "signal_ids": [201, 205],
 "scores": {"수요": 4, "차별성": 4, "실현성": 3, "규제": 5, "수익화": 3, "재사용": 2},
 "status": "draft", "reason": null, "doc_path": null}
```

동작:

1. 파일 전체를 먼저 검증하고, 하나라도 틀리면 **아무것도 쓰지 않는다**(줄 번호와 사유를 내고 종료). 쓰기는 검증을 다 통과한 뒤 `with conn:` 한 트랜잭션으로 한다.
2. 검증 — `title` 비어 있지 않고 **파일 안에서 중복되지 않음** / `status` ∈ `draft`·`shortlist`·`validating`·`dropped` / `signal_ids` 는 정수 배열이고(빈 배열 허용) 값이 있으면 그 주제의 `signal` 에 실재 / `scores` 는 객체 또는 null / `dropped` 면 `reason` 필수 / `shortlist` 면 `doc_path` 필수.
3. 적재 — `(topic, title)` 이 이미 있으면 **파일에 담긴 키만** UPDATE 한다. 없는 키는 건드리지 않는다 — 단계 15 의 상태 갱신 줄이 `jtbd`·`lens`·`scores` 를 null 로 지우지 않게 하는 장치다. 값을 비우려면 파일에 `null` 을 명시한다(키가 없는 것과 구분한다). 없으면 INSERT 하고 `created_at` 을 `db.utc_now()` 로 넣는다(다른 테이블과 같은 ISO 형식).
   - 새 행을 만드는 줄에는 `signal_ids`·`status` 가 반드시 있어야 한다. 갱신하는 줄에는 바꿀 키만 있으면 된다.
   - `dropped`·`shortlist` 로 바꾸는 줄은 `reason`·`doc_path` 를 **같은 줄에 담는다**. 검증은 DB 가 아니라 파일만 보므로, 기존 행에 값이 있어도 줄에 없으면 거부된다.
4. 출력 — `추가 N · 갱신 M · 전체 K`. `cli._log` 가 `log.md` 에 한 줄 남긴다.
5. 빈 파일·빈 줄만이면 예외 없이 `적재할 아이디어 없음` 으로 끝낸다. 파일이 없으면 경로를 담은 에러로 끝낸다.
6. `export`/`import` 와 달리 공통 경로를 타므로 `topics/<주제>/config.json` 이 있어야 한다(`top`·`funnel` 과 같다). `GitHub` 객체가 만들어지지만 생성자는 네트워크를 쓰지 않는다(`github.py:74`).

스키마는 바꾸지 않는다. `(topic, title)` UNIQUE 를 거는 대신 코드에서 조회 후 갱신한다 — 마이그레이션 없이 문제 4 가 해결되고, `import` 가 기존 `data/idea.jsonl` 을 그대로 받아들인다.

`title` 이 갱신 키이므로 **적재 후에는 제목을 바꾸지 않는다**. 제목이 바뀌면 옛 행이 `draft` 로 남는다. 스킬에 규칙으로 적는다.

#### 개선 코드

```python
# labbook/idea.py (신규, 요지)
import json
from labbook import db

STATUS = ("draft", "shortlist", "validating", "dropped")
COLS = ("jtbd", "lens", "signal_ids", "scores", "status", "reason", "doc_path")
REQUIRED = ("signal_ids", "status")   # 새 행을 만들 때 반드시 있어야 하는 키
JSON_COLS = ("signal_ids", "scores")


def load(conn, topic, path):
    if not path.exists():
        raise ValueError(f"아이디어 파일이 없다: {path}")
    known = {r[0] for r in conn.execute("SELECT id FROM signal WHERE topic = ?", (topic,))}
    titles, rows = set(), []
    for n, line in enumerate(path.read_text().splitlines(), 1):
        if not line.strip():
            continue
        try:
            r = json.loads(line)          # 줄 단위로 파싱해야 줄 번호를 붙일 수 있다
        except ValueError as e:
            raise ValueError(f"{path}:{n} JSON 이 아니다 — {e}") from None
        cur = conn.execute("SELECT id FROM idea WHERE topic = ? AND title = ?",
                           (topic, r["title"])).fetchone() if isinstance(r, dict) and r.get("title") else None
        _check(n, r, known, titles, is_new=cur is None)   # 전부 검증한 뒤에 쓴다
        titles.add(r["title"])
        rows.append((r, cur))
    added = updated = 0
    with conn:                            # 검증을 모두 통과한 뒤 한 트랜잭션으로 쓴다
        for r, cur in rows:
            cols = [c for c in COLS if c in r]   # 파일에 담긴 키만 건드린다 — 없는 필드를 null 로 덮지 않는다
            vals = [json.dumps(r[c], ensure_ascii=False) if c in JSON_COLS else r[c] for c in cols]
            if cur:
                conn.execute(f"UPDATE idea SET {', '.join(c + ' = ?' for c in cols)} WHERE id = ?", (*vals, cur["id"]))
                updated += 1
            else:
                conn.execute(f"INSERT INTO idea (topic, title, {', '.join(cols)}, created_at) "
                             f"VALUES (?, ?, {', '.join('?' * len(cols))}, ?)", (topic, r["title"], *vals, db.utc_now()))
                added += 1
    total = conn.execute("SELECT COUNT(*) FROM idea WHERE topic = ?", (topic,)).fetchone()[0]
    return {"added": added, "updated": updated, "total": total}
```

    s.add_argument("topic")

    ...

### 3.5 `toolkit.md` — 노트 기반, P≥4 를 다룬다

대상은 **P≥4 인 12개 + worldmonitor**(정밀 판정이 없어 심층 T 4 로 판단)다. 실제 설치·구동은 하지 않는다 — 실행법은 19개 노트의 설치·의존성·데이터 소스 기록에서 가져오고, 실제 사용 여부는 §2.3 두 번째 가설(판정일 2026-11-21)이 잰다.

### 5.2 근거

- 서브에이전트 분할은 3차에서 이미 검증됐다(레포당 4~10분, 19개 약 35분, 구독 한도 무사). 렌즈 7개는 3차의 19개보다 작다. 서로의 출력을 보지 않는 구조가 문제 2(앵커링)에 직접 대응한다.
- `idea-load` 는 이번 회차가 **실제로 idea 행을 쓰는 첫 회차**라서 지금 만드는 것이 가장 싸다. 적재를 두 번(draft → shortlist/dropped) 하므로 갱신 경로가 어차피 필요하고, 그 로직을 문서 속 heredoc 에 두면 문제 3 ③이 반복된다.
- `signal-load` 까지 같이 올리면 4차가 조사 실행과 코드 작업 두 덩어리가 된다. `signal` 은 이번 회차에 새로 쓰지 않으므로 미룬다.
- 툴킷을 노트 기반으로 두는 이유는 실행 검증의 값이 §2.3 두 번째 가설(4주 실사용)에서 나오기 때문이다. 미리 12개를 설치해도 KRX 로그인 같은 외부 변수 때문에 그 시점의 사실이 유지되지 않는다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- **리스크 1: 렌즈 7개가 같은 아이디어를 낸다.** "AI 신호 성적표"는 신뢰·검증과 GuruNote결합 양쪽에서 나올 수 있다. / 대응: 군집·중복제거에서 대표 하나만 남기고 합쳐진 렌즈를 대표에 모두 적는다. 대표가 12개 미만이면 발산이 쏠린 것이므로 그 사실을 후보표에 적고 사용자에게 알린다.
- **리스크 2: 서브에이전트가 근거 없는 아이디어를 낸다.** / 대응: `signal_ids` 필수이고, 메인이 적재 전에 `signals.tsv` 와 대조한다. `idea-load` 검증 4가 DB 수준에서 한 번 더 막는다.
- **리스크 3: 규제 라벨을 잘못 붙인다.** 유료 비개인화 추천을 "무료 정보·도구"로 읽으면 신고 의무를 놓친다. / 대응: 라벨 근거를 GuruNote §4(2024-08-14 시행 개정 자본시장법) 인용으로 적게 하고, 메인이 상위 6개는 다시 본다. 판단이 갈리면 보수적으로(더 무거운 라벨) 적는다.
- **리스크 4: 신호 쏠림이 JTBD 에 그대로 남는다.** / 대응: §3.1 의 레포 수·50% ⚠ 규칙과 수요 근거 상한 3. 성공 기준에 "레포 2곳 이상 70%"를 넣어 사후 확인한다.
- **리스크 5: 사용자가 3개를 못 고른다.** / 대응: 억지로 쓰지 않는다. §2.3 접을 기준대로 멈추고 입력·렌즈를 재검토한 뒤 다시 발산한다. 그 경우에도 `idea` 행과 `toolkit.md` 는 남긴다.
- **리스크 6: `title` 갱신 키.** 제목을 고치면 옛 행이 `draft` 로 남는다. / 대응: 스킬에 "적재 후 제목 불변" 규칙을 적고, 단계 15 뒤에 `draft` 로 남은 행 수가 예상과 맞는지 확인한다.
- **리스크 7: `.cache/brainstorm/` 은 gitignore 다.** 중간 산출물이 날아가면 발산을 다시 해야 한다. / 대응: JTBD 표와 후보표는 완료 시 원페이저·`idea` 행으로 정본이 남는다. 발산 도중 중단되면 남아 있는 `ideas-*.jsonl` 부터 이어서 한다(렌즈 단위 재개).
- **리스크 8: `signal_ids` 는 외래키가 아니다.** 적재 시점에만 실재를 확인하므로, 나중에 신호를 보강·재적재하다 id 가 바뀌면 원페이저의 근거(§2.2)가 조용히 끊긴다 — 옛 신호 행을 정리하는 경로가 아직 없다(PR #5 향후 작업 2번). / 대응: 이번 회차는 신호를 새로 쓰지 않으므로 발생하지 않는다. 신호를 다시 적재하는 계획에서 `idea.signal_ids` 재검사를 작업 행으로 넣는다.
