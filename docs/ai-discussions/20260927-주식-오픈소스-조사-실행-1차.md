### 1.2 문제점

- 문제 1 — **재현율 기준이 대부분 구조상 통과한다.**
  - 사용자 스타와 awesome 두 목록은 `collect` 가 그대로 수집하는 소스다. 그래서 이 두 부분은 버그가 없으면 항상 100% 잡힌다.
  - 쿼리 커버리지를 실제로 재는 것은 부록 A 27개뿐이다. 그런데 기준 목록 전체(awesome ≥1000★ 가 수백 개로 예상)에 5% 를 적용하면, 부록 A 를 여러 개 놓쳐도 통과한다.
  - 예: 전체 200개 중 부록 A 5개 누락이면 2.5% 로 통과한다. 하지만 부록 A 만 보면 18.5% 누락이다.
- 문제 2 — **한국 축은 기준 목록으로 재지 못한다.** 기준 목록의 한국 레포는 FinanceDataReader·prism-insight 2개뿐이고, 둘 다 사용자 스타라서 구조상 잡힌다.
  - 원 계획 §7.1 의 대응은 "재현율 점검에서 한국 축을 따로 본다"였다. 그런데 방법은 정하지 않았다.

- 문제 3 — **`collect` 는 전체를 한 트랜잭션으로 끝에 커밋한다.** awesome 링크를 조회하다 404 가 아닌 오류(DMCA 451, 차단 403 등)가 나면 `GitHubError` 로 멈춘다. 그러면 그때까지 모은 것도 남지 않는다(`collect.py:18` 은 `NotFound` 만 잡는다). 1,065개를 조회하므로 한 번쯤 걸릴 수 있다.

## 2. 목표

### 2.1 달성 목표

- 재현율 기준 목록을 만들어 커밋한다. 이후 주간 재실행과 다음 주제의 점검 기준이 된다.
- `collect` → `refresh` 로 후보 전체의 스냅샷과 범위 컷을 만든다. 재현율을 점검하고, 누락이 기준을 넘으면 쿼리를 보강해 다시 돌린다.
- 범위 내 레포 전부에 1단 선별을 돌린다.
- 결과를 `data/*.jsonl` 로 커밋한다. 골드셋 대표 8개 후보를 카테고리별로 제안하고 사용자에게 넘긴다.

### 2.2 성공 기준

- 재현율(원 계획 §2.2): 기준 목록 전체에서 `entity` 누락이 5% 이하다.
- 재현율(보강, §3.2): 부록 A 섹션 누락이 1개 이하다(27개 중 5% 이하).
- 기준 목록의 모든 레포가 `screening(scoped)` 에서 `include` 다. 예외는 archived·gone 뿐이고, 그 사유를 기록한다. 기준 목록은 전부 ≥1000★ 이거나 사용자 스타이므로 include 여야 한다.
- 한국 출처(`kr:`) 엔티티 수를 기록한다. 보강 쿼리는 첫 `collect` 전에 넣으므로 "보강 전" 실행이 없다. 대신 `identified.sources` 로 나눠 센다: 기존 10개 쿼리로 잡힌 수, 추가 8개로만 잡힌 수.
- `screening(triaged)` 의 `error` 는 재시도 2회 뒤 남은 것만 있다. 남은 것은 레포·`reason` 을 인계 문서와 PR 본문에 적는다. 대기열이 `error` 를 매번 다시 넣기 때문에(`judge.py:92-94`), 계속 실패하는 레포가 있으면 0건에 도달하지 못한다. 예: refresh 뒤에 삭제돼 404 가 나는 레포.
- `data/*.jsonl` 을 커밋하고, `import` 로 복원해서 같은 행 수가 나오는지 확인한다.
- 전체 테스트가 통과한다. 코드를 바꾸지 않으면 135개이고, §3.5 를 적용하면 136개다.

## 3. 해결 방안

### 3.1 기준 목록 작성

작성 스크립트는 스크래치패드에서 한 번 돌리고 커밋하지 않는다. 결과 파일만 커밋한다. `labbook.github.GitHub` 를 재사용해 링크 추출·이름 정규화를 `collect` 와 같게 맞춘다.

형식은 `owner/repo` 한 줄씩이다. `# [섹션]` 줄로 출처를 나누고 `#` 줄은 주석이다. 한 레포는 처음 나온 섹션에만 적는다. 그래서 부록 A 섹션에는 사용자 스타와 겹치지 않는 27개만 들어간다.

```
# 재현율 기준 목록 — 2026-09-27 작성. 이름은 작성일 repo API 기준 최신 full_name
# stars·awesome 섹션은 collect 소스와 같아 구조상 잡힌다(파이프라인 점검용). 쿼리 커버리지는 appendix-a 로 본다
# [stars] 사용자 스타 중 금융 (원 계획 §1.1)
virattt/ai-hedge-fund
…
# [appendix-a] 원 계획 부록 A — 사용자 스타와 겹치는 4개 제외
ZhuLinsen/daily_stock_analysis
…
# [awesome] wilsonfreitas/awesome-quant · georgezouq/awesome-ai-in-finance 링크 중 ≥1000★ (작성일 기준)
…
```

```python
# 스크래치: 기준 목록 작성 (레포 루트에서 실행)
from labbook.github import GitHub, GitHubError, NotFound

STARS = ["virattt/ai-hedge-fund", "TauricResearch/TradingAgents", "HKUDS/Vibe-Trading", "HKUDS/AI-Trader",
         "dragon1086/prism-insight", "Nunchi-trade/auto-researchtrading", "Y-Research-SBU/QuantHarness",
         "shiyu-coder/Kronos", "666ghj/MiroFish", "financial-datasets/mcp-server",
         "FinanceData/FinanceDataReader", "koala73/worldmonitor"]
APPENDIX_A = [...]  # 원 계획 부록 A 31개 그대로

gh, seen, lines = GitHub(), set(), [HEADER]
def add(section, names):
    lines.append(f"# [{section}] …")
    for n in names:
        if n.lower() not in seen:
            seen.add(n.lower()); lines.append(n)

add("stars", STARS); add("appendix-a", APPENDIX_A)
awesome = []
for lst in ("wilsonfreitas/awesome-quant", "georgezouq/awesome-ai-in-finance"):
    for link in gh.awesome_links(lst):
        try:
            r = gh.repo(link)
        except NotFound:
            continue
        except GitHubError as e:           # 문제 3 의 사전 탐지 — collect 에서도 멈출 링크
            print("조회 실패", link, e); continue
        if (r["stars"] or 0) >= 1000:
            awesome.append(r["full_name"])
add("awesome", sorted(awesome, key=str.lower))
open("topics/stock-oss/recall-baseline.txt", "w").write("\n".join(lines) + "\n")
```

archived 레포도 기준 목록에 남긴다. 점검 대상은 수집(`entity`)이고, archived 는 범위 컷에서 사유와 함께 빠지기 때문이다.

### 3.2 재현율 점검

기준 목록을 `entity`·`screening` 과 대조한다. 섹션마다 아래를 낸다.

- 수, 누락 목록
- 검색으로도 잡혔는지(`sources` 에 `search:`·`kr:` 가 있는지)
- 범위 컷 결과

**판정 규칙** (2026-09-27 사용자 확정)

| 섹션 | 누락의 의미 | 조치 |
|---|---|---|
| 전체 | 원 계획 기준 | 5% 초과면 쿼리를 보강한다 |
| appendix-a | 쿼리 커버리지 부족 | 2개 이상이면 쿼리를 보강한다 |
| stars·awesome | 구조상 잡혀야 한다. 누락이면 파이프라인 버그다 | 쿼리가 아니라 코드를 고친다(작은 수정은 바로, 크면 별도 계획) |

근거: 문제 1 대로 전체 5% 는 부록 A 누락을 가린다. 앞으로 새로 뜨는 레포는 검색으로만 들어온다. 그래서 검색 커버리지를 대표하는 것은 부록 A 다.

```python
# 스크래치: 재현율 점검 (collect·refresh 뒤, 보강 반복 때마다)
import sqlite3
conn = sqlite3.connect("labbook.db")
SQL = """SELECT i.sources, sc.decision, sc.reason FROM entity e
  JOIN screening i ON i.entity_id = e.id AND i.topic = 'stock-oss' AND i.stage = 'identified'
  LEFT JOIN screening sc ON sc.entity_id = e.id AND sc.topic = 'stock-oss' AND sc.stage = 'scoped'
  WHERE e.key = ?"""
section, rows = None, []
for line in open("topics/stock-oss/recall-baseline.txt"):
    line = line.strip()
    if line.startswith("# ["):
        section = line[3:line.index("]")]
    elif line and not line.startswith("#"):
        rows.append((section, line, conn.execute(SQL, (f"github:{line.lower()}",)).fetchone()))
# 섹션별: 수 · 누락 목록 · 검색으로 잡힌 수(search:/kr:) · scoped include 가 아닌 것(사유)
```

**보강 방법**: 누락 레포의 토픽·설명을 보고 `config.json` 에 토픽이나 키워드 쿼리를 더한다. 그다음 `collect` → `refresh` 를 다시 돌린다.
- `collect` 는 멱등이다. 출처가 누적될 뿐이다.
- 같은 날 `refresh` 는 이미 스냅샷이 있는 레포를 건너뛴다. 그래서 새 후보만 API 를 부른다.
  - "같은 날"은 실행을 시작한 시점의 UTC 날짜다(`metrics.py:62`). 한국 시간으로는 매일 09:00 에 날짜가 바뀐다.
  - 보강 반복의 `refresh` 는 첫 `refresh` 와 같은 UTC 날짜에 시작해야 한다. 날짜가 바뀐 뒤 시작하면 후보 전체를 다시 조회해서 약 2시간이 더 든다.
  - 날짜가 이미 바뀌었으면 그대로 진행하되, 소요를 사용자에게 먼저 알린다.
- 보강은 최대 2회로 한다. 그래도 기준을 넘으면 남은 누락 레포와 원인(검색 색인 누락 등)을 인계 문서 §3 과 PR 본문의 재현율 표에 적는다. 그다음 사용자에게 넘긴다.
  - 사용자 스타가 아닌 레포는 범위 컷 `include` 를 받을 경로가 없다. 그래서 넣을지(예: 사용자가 스타를 누른다, 또는 다음 조각의 `select --add`) 는 사용자가 정한다.

### 3.4 실행 순서와 소요

| 명령 | 예상 규모 | 실행 방식 |

- `triage` 가 끝나면 카테고리 분포를 뽑는다. 골드셋 대표 8개 후보를 제안한다.
  - 규칙: 사용자 스타가 아니고, `include` 이고, 레포가 많은 카테고리 8개에서 ★ 최상위를 하나씩 고른다.
  - 사용자는 이 후보를 보고 바꿀 수 있다. 채점은 사용자가 한다(다음 조각).
- 마지막으로 `20260927-세션-인계.md` 의 §1 상태와 §3 진행 표시를 갱신한다.

### 3.5 collect 의 non-404 오류 처리 (collect 가 멈출 때만)

`collect` 가 awesome 링크 조회에서 `GitHubError` 로 멈춘 경우에만 적용한다. 미리 넣지 않는다(2026-09-27 사용자 확정). 기존 절단 경고와 같은 경로를 쓴다: `collect()` 가 요약에 목록을 담아 돌려주고, `cli` 가 stderr 로 찍는다.

## 7. 리스크 및 고려사항

### 7.1 잠재적 리스크

- `collect` 가 `GitHubError` 로 멈추고, 수집분이 남지 않는다(문제 3). / 대응: 2단계 스크래치가 두 목록(755개 링크)을 먼저 조회하므로 대부분 미리 드러난다. 멈추면 §3.5 수정을 한다(멈출 때만 — 2026-09-27 사용자 확정).
- `refresh` 중 core 한도 소진으로 대기한다. / 대응: 어댑터가 리셋까지 기다린다.
  - 한 번의 실행은 시작 시점의 UTC 날짜를 끝까지 쓴다. 그래서 실행 중에 자정을 넘겨도 스냅샷 날짜가 갈리지 않는다.
  - 세션이 끊겨 재실행할 때는 같은 UTC 날짜(KST 09:00 전)에 시작해야 이어진다. 날짜가 바뀐 뒤면 처음부터 다시 조회한다. 결과에는 해가 없고 시간만 더 든다(§3.2).
- 쿼리 보강으로 후보가 늘어 `refresh` 가 길어진다. / 대응: 같은 날 재실행이라 새 후보만 조회한다.
- 1단 sonnet 호출이 구독 한도를 쓴다(약 40회). / 대응: `--limit 200` 회차마다 멈출 수 있다. 판정은 묶음 단위로 커밋된다.
- `자동매매`·`주식 in:readme` 가 크립토·튜토리얼을 끌어온다. / 대응: 수십 건 규모다. 1단에서 걸러지고 제외 사유가 퍼널에 남는다.

### 7.2 의존성

- `gh`(github.com 로그인), `claude` CLI 로그인 세션, Python 3.14, `sqlite3`.
- 하네스: 이번 계획처럼 코드 변경 없는 운영 실행에는 plan-execute 의 TDD 단계가 맞지 않는다. 6장에 확인 열을 둬서 대신했다. 이런 사례가 모이면 indie-forge 에 "운영 실행 계획" 형식을 제안한다.

### 7.3 범위 밖 / 향후 작업

- 인계 §3 7단계부터(골드셋 채점·보정·정밀 판정·select·심층분석·브레인스토밍)는 다음 조각이다. 골드셋 채점 결과를 받은 뒤 연다.
- 재현율 점검을 `labbook recall <topic>` 명령으로 승격하는 일. 주간 재실행이나 다음 주제에서 두 번째로 쓰일 때 한다.
- 한국 축의 독립 기준 목록(예: 수동 큐레이션). 1단 `market=kr` 결과를 보고 부족하면 한다.
